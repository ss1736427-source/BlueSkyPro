# BlueSky PRO — Multi-UAV Zonal Route Generation

**ID:** PLAN-MULTI-007  
**Status:** BASELINED  
**Scope:** deterministic planning core

## 1. Purpose

For coordinated multi-UAV missions, BlueSky PRO shall first partition the applicable mission operating area into non-overlapping operational zones/sectors and assign one zone to each participating UAV.

The primary deconfliction objective is therefore achieved during route generation:

`MISSION/COVERAGE -> CONSTRAINED OPEN SPACE -> ZONE PARTITION -> UAV ZONE ASSIGNMENT -> ROUTE-IN-ZONE -> WIND/PERFORMANCE -> 4D VERIFY`

The previously established ground-only conflict-resolution policy remains the fallback when clean zonal planning is infeasible.

## 2. Zone contract

Each zone is a versioned planning object containing:
- area identity/version;
- zone identity/version;
- ordered boundary geometry;
- deterministic ordinal.

Each UAV assignment contains:
- UAV identity;
- assigned zone identity;
- assignment version.

Zone boundaries and assignments carry calculation/dependency identity and are reusable until a relevant dependency changes.

## 3. Deterministic partition baseline

The initial implementation provides a deterministic equal-width partition of the area's bounding rectangle into one sector per UAV.

UAV IDs are sorted before assignment so that the same inputs produce the same assignment independent of input order.

This is an implementation baseline, not a claim that equal-width partition is the final coverage optimizer. Future partition strategies may replace it under the same contract if they preserve:
- non-overlapping zones;
- deterministic/versioned output;
- constrained-open-space compatibility;
- traceable dependencies.

## 4. Route-in-zone requirement

A route assigned to a zone shall remain inside that zone in addition to all existing:
- constrained-open-space restrictions;
- terrain/obstacle constraints;
- altitude limits;
- mandatory waypoint requirements;
- UAV capability/performance constraints;
- authorization-qualified regulatory constraints.

Zone boundaries do not grant airspace permission and cannot override any independent hard constraint.

## 5. Conflict fallback

If non-overlapping zones cannot preserve mission feasibility/coverage, the planner shall invoke the established ground-only conflict-resolution policy:
1. minimum necessary start delay, maximum 5 seconds;
2. continuous 4D conflict recheck;
3. vertical correction where applicable;
4. return to the original profile after the affected conflict segment;
5. continuous 4D recheck;
6. unresolved conflict blocks readiness.

No reactive in-flight conflict command is generated by this planning layer.

## 6. Recalculation

The zone partition is calculated once at the architectural level where mission area and participating UAV set are known.

A change to:
- mission geometry;
- participating UAVs;
- relevant hard constraints;
- authorization-qualified environment;
- coverage requirements

invalidates the affected zone assignment and downstream route calculations. Unaffected results remain reusable under the calculation-reuse baseline.

## 7. Authority boundary

This component:
- does not authorize flight;
- does not change regulatory restrictions;
- does not bypass physical obstacles;
- does not set READY;
- does not execute UAV commands.

It is a deterministic planning result consumed by route generation and subsequent validation.
