# ARCH-028 — HUB Resource and Safety-Critical Load Management

## 1. азначение

ARCH-028 определяет принципы управления вычислительными, коммуникационными и иными ресурсами HUB Core с приоритетом обеспечения безопасности и надёжности жизненно важных функций .

Система должна обеспечивать управляемую деградацию при перегрузке, отказах или ограничении ресурсов.

## 2. сновной принцип

аспределение ресурсов HUB должно выполняться по критичности функций, а не только по вычислительной нагрузке.

ункции, необходимые для безопасного управления полётом и сохранения управляемости , имеют приоритет над mission, AI, аналитическими и фоновыми функциями.

AI, самообучение и аналитические процессы не должны иметь возможности ухудшить выполнение safety-critical функций.

## 3. лассы приоритетов

### P0 — Safety Critical

- аварийные функции
- предотвращение опасных состояний
- safety monitoring
- критические защитные функции

### P1 — Flight / Navigation / C2

- flight control
- navigation
- positioning
- C2
- потеря связи и аварийные процедуры

### P2 — Mission

- mission execution
- task allocation
- replanning
- fleet coordination

### P3 — Situational Awareness

- perception
- tracking
- mapping
- sensor fusion

### P4 — AI / Analytics

- AI inference
- predictive analysis
- optimisation
- recommendation

### P5 — Background

- архивирование
- вторичная аналитика
- синхронизация
- обслуживание
- фоновые задачи

## 4. есурсы

HUB должен управлять как минимум следующими ресурсами:

- CPU
- GPU
- RAM
- storage
- network bandwidth
- message queues
- processing time
- external service capacity

## 5. езервирование ресурсов

ля P0 и P1 должны резервироваться минимально необходимые ресурсы.

езерв не должен быть доступен для произвольного использования задачами более низкого приоритета.

есурсные резервы должны учитывать текущий operational profile и состояние системы.

## 6. Graceful Degradation

ри недостатке ресурсов система должна снижать нагрузку по принципу приоритета.

 первую очередь должны ограничиваться P5 и P4.

атем при необходимости могут ограничиваться P3.

P2 должен сохраняться в объёме, необходимом для безопасного выполнения миссии.

P1 и P0 должны сохраняться в требуемом объёме независимо от нагрузки низкоприоритетных функций.

## 7. ащита flight-critical функций

AI, машинное обучение, самообучение и аналитические процессы должны выполняться в изолированном ресурсном контуре.

AI-процесс не должен иметь возможности занять ресурсы, зарезервированные для flight control, navigation, C2 или safety.

ри обнаружении ресурсного конфликта AI и аналитические процессы должны автоматически ограничиваться или приостанавливаться.

## 8. Самообучение

роцессы самообучения должны выполняться только при наличии достаточного свободного ресурса.

бновление моделей не должно выполняться таким образом, чтобы нарушить критические функции системы.

овая модель должна проходить контролируемую проверку до её использования в критическом operational loop.

Самообучение не должно автоматически изменять safety-critical поведение без предусмотренного механизма валидации, контроля версии и отката.

## 9. Watchdog

HUB должен иметь механизм контроля зависших, перегруженных или отказавших сервисов.

Watchdog должен контролировать как минимум:

- CPU load
- GPU load
- memory
- queue saturation
- network saturation
- service heartbeat
- processing latency
- service health

## 10. ащита от перегрузки

ри достижении установленных порогов HUB должен инициировать управляемое снижение нагрузки.

Система должна предотвращать каскадную перегрузку сервисов.

ерегрузка одного некритичного сервиса не должна приводить к отказу критических сервисов.

## 11. Latency Management

ля критических сообщений должны устанавливаться допустимые задержки.

P0 и P1 должны иметь более строгие требования к latency, чем P3–P5.

ри росте задержки критического сервиса система должна предпринимать защитные действия.

## 12. Communication Resource Management

ропускная способность каналов связи должна распределяться с учётом приоритета сообщений.

P0 и P1 должны иметь гарантированный приоритет перед P4 и P5.

ри ограниченной полосе пропускания низкоприоритетный трафик должен ограничиваться или откладываться.

## 13. Storage Management

HUB должен обеспечивать защиту пространства хранения для критических журналов, telemetry, audit и safety events.

оновые данные не должны иметь возможность полностью заполнить хранилище.

олжны поддерживаться политики retention и controlled deletion.

## 14. HUB-A / HUB-B

аспределение ресурсов должно учитывать отказоустойчивую архитектуру HUB-A/HUB-B.

ри переходе на резервный HUB критические сервисы должны получать приоритет восстановления.

екритичные сервисы могут запускаться после восстановления P0/P1/P2.

## 15. Health-Based Resource Management

аспределение ресурсов должно учитывать состояние оборудования и сервисов.

ри ухудшении health state система должна автоматически пересматривать допустимую нагрузку.

есурсная политика должна учитывать:

- thermal state
- power state
- compute health
- communication health
- storage health
- service health

## 16. Mission-Aware Resource Management

аспределение ресурсов должно учитывать текущую фазу миссии.

 критических фазах миссии требования P0/P1/P2 могут получать повышенный ресурсный приоритет.

ри завершении критической фазы ресурсы могут перераспределяться на другие задачи.

## 17. Resource Arbitration

HUB должен иметь централизованный механизм разрешения конфликтов за ресурсы.

ва или более сервиса не должны самостоятельно конкурировать за критический ресурс без участия Resource Manager.

## 18. онтроль изменений

зменение ресурсных политик должно быть версионируемым и журналируемым.

ритические изменения должны иметь возможность отката.

## 19. аблюдаемость

HUB должен предоставлять информацию о ресурсной нагрузке и причинах деградации.

ля критических событий должна сохраняться трассировка:

Resource Pressure → Arbitration → Degradation → Recovery

## 20. осстановление

осле снятия перегрузки система должна восстанавливать ограниченные сервисы контролируемым образом.

осстановление не должно создавать вторичную перегрузку.

ритические функции должны восстанавливаться раньше низкоприоритетных.

## 21. езопасность

зменение resource policy должно быть разрешено только авторизованным компонентам.

опытки несанкционированного изменения приоритетов или ресурсных лимитов должны регистрироваться.
