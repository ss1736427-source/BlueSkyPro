# ARCH-030 — Unified Operational Data Utilization for Planning and Situation Awareness

## 1. Назначение

ARCH-030 фиксирует принцип использования всех доступных и пригодных данных от БПЛА, наземного оборудования, внешних источников и накопленной истории для повышения точности, эффективности и безопасности планирования BlueSky PRO.

Принцип действует до полёта, во время полёта и после полёта.

## 2. Основной принцип

BlueSky PRO не должен ограничивать планирование только заранее заданными картами, прогнозами и паспортными характеристиками БПЛА.

Все доступные данные, которые способны улучшить планирование или оценку ситуации, должны рассматриваться системой при условии проверки их качества, актуальности, происхождения и применимости.

Отсутствие конкретного типа оборудования не должно ломать систему. Наличие дополнительного оборудования должно расширять доступную системе ситуационную информацию и набор возможных расчётов.

## 3. Источники данных

### 3.1. Бортовые данные БПЛА

Могут использоваться:
- telemetry;
- GNSS/GPS/Galileo/GLONASS/BeiDou;
- RTK/PPK;
- IMU/INS;
- airspeed;
- barometric altitude;
- battery/power;
- ESC;
- motor/propulsion state;
- flight-controller state;
- RGB/video cameras;
- stereo/depth cameras;
- low-light/night vision;
- NIR;
- thermal/IR;
- LiDAR;
- radar;
- ultrasonic/range sensors;
- acoustic sensors;
- environmental sensors;
- payload telemetry;
- иные доступные сенсоры и измерительные системы.

Список является открытым.

### 3.2. Наземные данные

Могут использоваться:
- метеостанции;
- наземные датчики ветра;
- камеры;
- LiDAR/radar;
- данные наземного оборудования;
- данные о посадочных площадках;
- техническое состояние оборудования;
- операторские наблюдения;
- иные доступные источники.

### 3.3. Внешние данные

Могут использоваться:
- прогнозы погоды;
- wind models;
- карты;
- terrain/elevation;
- NOTAM;
- restricted areas;
- известные препятствия;
- иные внешние источники.

### 3.4. Накопленные данные

Должны использоваться, когда они применимы к текущей задаче:
- результаты предыдущих миссий;
- фактический ветер;
- фактическое энергопотребление;
- фактическое поведение propulsion;
- фактические навигационные отклонения;
- обнаруженные препятствия;
- проверенные посадочные зоны;
- operator corrections;
- maintenance data;
- исторические environmental conditions;
- успешные и неуспешные решения;
- другие подтверждённые эксплуатационные наблюдения.

## 4. Контур обработки данных

Базовый контур:

Data Acquisition
→ Data Quality
→ Data Fusion
→ Situation / Flight Knowledge
→ Planning Intelligence
→ Plan / Recommendation
→ Flight
→ Observation
→ Learning / Model Update

После полёта фактические данные возвращаются в систему для последующего планирования.

## 5. Data Quality и Confidence

Данные не должны автоматически влиять на критические расчёты только потому, что они доступны.

Для применяемого наблюдения по возможности должны сохраняться:
- source;
- timestamp;
- position/context;
- validity;
- accuracy;
- freshness;
- source reliability;
- sensor health;
- confidence;
- applicability.

Некачественные, противоречивые или неподтверждённые данные не должны автоматически изменять критические модели.

## 6. Sensor Fusion

Если несколько источников описывают один объект или состояние, система должна иметь возможность сопоставлять и объединять их.

Пример:

Camera + LiDAR + Thermal
→ Object / Person
→ confidence

Противоречивые данные должны сохраняться как противоречие и проходить контролируемую обработку, а не автоматически считаться истинными.

## 7. Capability Profile БПЛА

Наличие оборудования должно быть частью capability profile конкретного БПЛА.

Пример:

UAV → RGB / Thermal / Night Vision / LiDAR / Radar / RTK / Airspeed / ...

Planning и Situation Awareness должны автоматически учитывать доступный набор источников.

Отсутствие сенсора означает отсутствие соответствующего наблюдения, а не ошибку системы.

## 8. Использование данных для планирования

Доступные данные могут повышать точность:
- выбора маршрута;
- альтернативных маршрутов;
- расчёта времени;
- расчёта высоты;
- расчёта скорости;
- wind correction;
- energy model;
- battery reserve;
- propulsion model;
- payload correction;
- navigation accuracy;
- obstacle avoidance;
- landing-site selection;
- risk assessment;
- contingency planning;
- mission allocation между несколькими БПЛА.

## 9. Фактический ветер и прогноз

Система должна иметь возможность сравнивать:

Forecast Wind ↔ Observed Wind

Фактические наблюдения могут использоваться для оценки ошибки прогноза и последующей корректировки planning models.

Накопленная статистика не должна без проверки применяться к другой местности, высоте, платформе или погодному режиму.

## 10. Энергетическая модель

Фактические данные battery/power, propulsion, speed, altitude, payload и environmental conditions могут использоваться для уточнения модели энергопотребления.

Система должна различать:
- прогнозное потребление;
- фактическое потребление;
- отклонение;
- подтверждённую модельную коррекцию.

## 11. Propulsion и состояние БПЛА

Состояние двигателей, ESC и другой propulsion equipment должно использоваться не только для диагностики, но и для оценки возможности выполнения планируемого режима полёта.

Данные могут включать:
- RPM;
- current;
- temperature;
- ESC state;
- actuator response;
- detected faults;
- propulsion capability.

Непосредственное управление propulsion и flight stabilization остаётся в зоне ответственности flight controller согласно базовой архитектуре адаптера.

## 12. Наземная обстановка и посадка

Данные камер, thermal, night vision, LiDAR, radar, depth и других сенсоров могут использоваться для оценки:
- людей;
- транспорта;
- животных;
- препятствий;
- зданий;
- линий;
- рельефа;
- состояния поверхности;
- иных наземных объектов.

Отсутствие обнаруженного человека не должно интерпретироваться как доказательство отсутствия людей.

Неизвестный или недостаточно классифицированный объект должен рассматриваться консервативно в соответствии с safety policy.

Для emergency landing оцениваются как посадочная зона, так и траектория подхода/снижения.

## 13. Planning Knowledge и история

Фактические результаты предыдущих полётов должны формировать накопленное operational knowledge.

Для каждого знания должна сохраняться применимость к:
- UAV/platform;
- payload;
- mission type;
- geography;
- altitude;
- environmental context;
- operational context.

Опыт одного типа БПЛА не должен автоматически считаться полностью применимым к другому типу без проверки.

## 14. Общие и индивидуальные модели

BlueSky PRO может использовать общие модели флота и индивидуальные поправки.

Базовый принцип:

Shared Model + Verified Platform-specific Corrections

Это позволяет использовать общий опыт без потери особенностей конкретного БПЛА.

## 15. Planning до, во время и после полёта

### До полёта

Используются текущие внешние данные, состояние БПЛА, наземные наблюдения и накопленный опыт для построения плана.

### Во время полёта

Фактические данные могут использоваться для monitoring, replanning, risk assessment, energy prediction, wind correction и contingency assessment в пределах утверждённых safety constraints.

### После полёта

План сравнивается с фактом. Отклонения анализируются, подтверждённые результаты поступают в накопленное знание и могут использоваться в следующих миссиях.

## 16. AI и данные

AI может использовать объединённые и проверенные данные для:
- поиска закономерностей;
- выявления отклонений;
- прогноза;
- формирования рекомендаций;
- поиска улучшений planning models;
- анализа повторяющихся corrections;
- оценки применимости накопленного опыта.

AI не должна самостоятельно изменять safety-critical поведение вне утверждённого lifecycle и approval process.

## 17. Разделение измерения и знания

Система должна различать:

RAW DATA
→ VERIFIED DATA
→ OBSERVATION
→ MODEL KNOWLEDGE

Одно наблюдение не должно автоматически становиться постоянным правилом планирования.

## 18. Traceability

Для значимого влияния данных на планирование должна быть доступна цепочка:

Source Data
→ Quality / Confidence
→ Observation
→ Planning Factor
→ Planning Result
→ Actual Result
→ Model / Knowledge Update

Это необходимо для анализа точности и аудита.

## 19. Safety boundary

Использование дополнительных данных не отменяет safety constraints.

Дополнительный сенсор может повысить качество оценки, но не должен автоматически получать право отменять обязательные ограничения.

При потере или деградации сенсора система должна переходить к корректно определённому уровню доступности данных и не создавать ложную уверенность.
