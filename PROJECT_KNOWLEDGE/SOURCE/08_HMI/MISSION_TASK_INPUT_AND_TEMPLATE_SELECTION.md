# BlueSky PRO — создание задачи и динамический выбор шаблонов миссии

**Статус:** зафиксированное UX-решение для последующих модификаций  
**Область:** HMI / левая панель создания задачи / подбор шаблонов  
**Принцип:** сначала оператор формулирует задачу; система анализирует её и подсвечивает шаблоны, которые потребуются для построения миссии.  
**Состав библиотеки:** 7 основных шаблонов + 4 дополнительных (всего 11).  
**Дата фиксации:** 2026-09-30

## 1. Утверждённая последовательность взаимодействия

1. Оператор открывает левую панель **«Создание задачи»**.
2. В верхнем поле вводит задачу естественным языком. Пример: «Обследовать территорию площадью 5 км²».
3. Система интерпретирует формулировку и извлекает цель, объект/геометрию, масштаб, ограничения и дополнительные условия, если они указаны.
4. На панели автоматически выделяются один или несколько релевантных шаблонов из библиотеки 7+4. Выделение означает, что шаблон задействован в предлагаемом плане, а не что оператор уже подтвердил запуск.
5. Система показывает краткое понимание задачи и выявленные пробелы/неоднозначности. Если обязательных данных не хватает, запрашивает только их.
6. На карте оператор уточняет геометрию и параметры задания. Связанные шаблоны и параметры обновляются по мере изменения задачи.
7. Перед построением/подтверждением миссии оператор видит, какие шаблоны задействованы, и может открыть их параметры, исключить необязательный шаблон или изменить исходную формулировку.
8. Система строит миссию и передаёт её на проверки планирования и безопасности. Подсветка шаблонов сама по себе не является разрешением на полёт.

## 2. Организация левой панели

### Верхний уровень — задача оператора
- Заголовок: **СОЗДАНИЕ ЗАДАЧИ**.
- Главное поле ввода — визуально доминирующий элемент панели.
- Текст задачи сохраняется и остаётся доступным при переходе к карте и параметрам.
- Очистка поля не должна незаметно удалять уже построенную миссию; требуется явное подтверждение, если есть несохранённые изменения.

### Библиотека шаблонов 7+4
- Все 11 шаблонов принадлежат единой библиотеке и доступны из левой панели.
- Визуальная группировка: **7 основных** и **4 дополнительных**. Это группировка отображения, а не два разных механизма планирования.
- Не показывать 11 крупных равноправных кнопок одновременно: панель должна сохранять приоритет задачи и карты.
- Основные шаблоны размещать в компактной группе; дополнительные — в раскрываемом блоке **«Ещё 4»**. Если дополнительный шаблон автоматически задействован, блок раскрывается или показывает заметный индикатор, чтобы выбранный элемент не оставался скрытым.
- Каждый шаблон имеет состояния: обычный, автоматически задействован, выбран оператором, требует данных, недоступен для текущего БВС/задачи.
- Состояние должно передаваться не только цветом: использовать контур/маркер/подпись состояния, сохраняя читаемость и доступность.
- Выделение автоматически задействованного шаблона не блокирует ручное открытие его параметров.

### Сводка подбора
После интерпретации показывать компактную строку/область:
- **Задействованы:** список шаблонов с визуальной связью с библиотекой.
- **Нужно уточнить:** только недостающие обязательные сведения.
- **Причина подбора:** короткое объяснение, почему шаблон включён, доступное по нажатию/раскрытию.
- Не показывать длинные объяснения постоянно и не перегружать экран.

## 3. Поведение автоматического подбора

- Подбор может активировать несколько шаблонов для одной операторской задачи.
- Шаблон описывает алгоритмический способ выполнения части задачи; он не должен дублировать другой шаблон с той же логикой.
- Система различает цель оператора и способ выполнения: формулировка задачи не обязана совпадать с названием шаблона.
- При неоднозначной формулировке система не должна молча фиксировать единственный вариант. Она показывает подходящие варианты и задаёт короткий уточняющий вопрос.
- При изменении текста, геометрии, параметров или доступности БВС подбор пересчитывается. Изменения уже подтверждённой миссии должны быть видимыми.
- Ручное переопределение оператора сохраняется в контексте текущей задачи; система не должна бесшумно отменять его при очередном пересчёте.
- Если шаблон несовместим с выбранным БВС, сенсором, типом миссии или ограничениями, показать причину и предложить допустимый путь, а не просто скрыть шаблон.
- Подбор шаблонов — рекомендательный механизм планирования. Геозоны, NOTAM, ограничения воздушного пространства, технические пределы БВС и safety-проверки имеют отдельный авторитетный статус и не обходятся выбором шаблона.

## 4. Правила визуального состояния

| Состояние | Представление | Смысл |
|---|---|---|
| Обычный | Нейтральный стиль | Шаблон доступен, но сейчас не задействован |
| Автоматически задействован | Акцентный контур/подсветка + маркер | Система включила шаблон в предлагаемый план |
| Подтверждён оператором | Акцент + отдельный маркер подтверждения | Оператор явно подтвердил использование |
| Требует данных | Предупреждающий индикатор и короткая подпись | Для применения не хватает параметров |
| Недоступен | Приглушённый стиль, причина по нажатию | Текущая конфигурация не поддерживает шаблон |

Не использовать один и тот же визуальный признак для «автоматически подобран» и «оператор подтвердил».

## 5. Принципы компоновки

- Поле задачи — первый и главный шаг; библиотека шаблонов не должна заставлять оператора выбирать алгоритм до формулировки цели.
- Карта остаётся центральной рабочей областью; левая панель не должна закрывать критическую часть карты без необходимости.
- Панель сохраняет контекст задачи при переходе между картой, параметрами и проверками.
- На планшете использовать компактную прокручиваемую панель; на ПК допускается более широкое представление, но логика последовательности та же.
- Не вводить отдельный модуль/архитектурный слой ради 7+4. Это поведение HMI поверх существующего механизма интерпретации задачи, библиотеки шаблонов и планировщика.
- Сохранять текущую визуальную систему BlueSky PRO; не добавлять декоративные элементы без функционального смысла.

## 6. Границы и данные, которые нельзя выдумывать

- Количество библиотеки зафиксировано: 7 основных + 4 дополнительных.
- Канонические названия и принадлежность каждого шаблона к группе должны браться из утверждённого перечня 7+4. Если в актуальном источнике нет полного перечня, не придумывать названия и не заменять их новыми.
- Данный документ фиксирует взаимодействие и состояния интерфейса, но не подменяет отдельные алгоритмические спецификации каждого шаблона.
- Алгоритм каждого шаблона должен быть описан отдельно: входные данные, предусловия, построение геометрии/траектории, ограничения, критерии качества, обработка ошибок, выходные данные и тесты.
- Любые автоматические рекомендации должны быть объяснимыми и проверяемыми; итоговая миссия проходит существующие проверки планирования и безопасности.

## 7. Критерии приёмки

1. Оператор может начать работу, введя задачу естественным языком, без предварительного выбора шаблона.
2. После интерпретации автоматически подсвечиваются все задействованные шаблоны из библиотеки 7+4.
3. Не задействованные шаблоны остаются доступными, но визуально не конкурируют с активными.
4. При изменении задачи/геометрии подсветка и состав предлагаемой миссии актуализируются.
5. Система показывает, почему шаблон задействован, и какие обязательные данные отсутствуют.
6. Автоматический подбор не выдаётся за подтверждение оператора и не означает разрешение на полёт.
7. Ручное переопределение явно сохраняется и не теряется при пересчёте.
8. Недоступность шаблона объясняется; система не скрывает несовместимость молча.
9. Представление остаётся читаемым на планшете и ПК, не перекрывая карту сверх необходимого.
10. Библиотека содержит ровно 11 шаблонов: 7 основных и 4 дополнительных; названия сверяются с утверждённым каталогом.

## 8. Связь с дальнейшей разработкой

- HMI: реализовать поле задачи, группировку 7+4, состояния шаблонов и краткую сводку подбора.
- Intent/task interpretation: преобразовать естественный язык в структурированное описание задачи с указанием уверенности и недостающих данных.
- Mission planning: сопоставить структурированную задачу с одним или несколькими шаблонами и собрать миссию.
- Template specifications: для каждого шаблона отдельно определить алгоритм выполнения и тесты.
- Verification: проверять правильность подбора, корректность обновления при редактировании, совместимость и отсутствие обхода safety-проверок.


## 9. Реализация и проверка в Qt Design Studio

### 9.1 Что должно быть видно в макете

Исходный экран «Формирование задачи» сохраняет текущую компоновку: поле задачи находится первым; ниже расположена библиотека шаблонов. Оператор не обязан нажимать шаблон до ввода задачи.

После ввода текста система выделяет задействованные шаблоны непосредственно в существующей библиотеке. Не добавлять второй список шаблонов и не дублировать кнопки. Для каждого задействованного шаблона использовать различимое состояние: акцентный контур/маркер плюс подпись или индикатор; одного изменения цвета недостаточно.

Если задействован шаблон из группы «Ещё», блок должен автоматически раскрыться либо показать явный индикатор наличия активного шаблона внутри. Активный шаблон нельзя оставлять незаметным внутри закрытого блока.

Макет Design Studio может демонстрировать состояния на тестовых примерах. Он не должен изображать распознавание естественного языка как уже реализованный алгоритм, если QML пока использует статические демонстрационные данные.

### 9.2 Матрица проверки макета

| ID | Действие / сценарий | Ожидаемый результат | Проверка |
|---|---|---|---|
| DS-TPL-01 | Открыть экран без введённой задачи | Ни один шаблон не обозначен как автоматически задействованный; все доступные шаблоны остаются доступными | Визуально |
| DS-TPL-02 | Ввести задачу, соответствующую одному шаблону | Подсвечивается соответствующий шаблон; текст задачи сохраняется | Визуально + взаимодействие |
| DS-TPL-03 | Ввести задачу, требующую нескольких алгоритмов | Подсвечены все задействованные шаблоны, а не только один | Визуально + взаимодействие |
| DS-TPL-04 | Задействовать шаблон из «Ещё 4» | Блок раскрывается или явно показывает активность внутри | Визуально + взаимодействие |
| DS-TPL-05 | Изменить текст задачи | Состав подсвеченных шаблонов обновляется; устаревшая подсветка снимается | Взаимодействие |
| DS-TPL-06 | Очистить поле при наличии созданной/изменённой миссии | Миссия не удаляется молча; при необходимости запрашивается подтверждение | Взаимодействие |
| DS-TPL-07 | Шаблону не хватает обязательных данных | Видимый индикатор «Нужны данные»; запрос касается только недостающих параметров | Визуально + взаимодействие |
| DS-TPL-08 | Шаблон несовместим с выбранным БВС | Шаблон не исчезает бесследно; причина недоступности доступна оператору | Визуально + взаимодействие |
| DS-TPL-09 | Оператор вручную переопределяет автоматический выбор | Ручное решение визуально отличается и сохраняется при обновлении подбора | Взаимодействие |
| DS-TPL-10 | Просмотреть экран на целевых размерах ПК/планшета | Поле задачи и активные шаблоны читаемы; панель не перекрывает критическую область карты | Проверка размеров |
| DS-TPL-11 | Проверить библиотеку | Ровно 7 основных + 4 дополнительных; названия соответствуют утверждённому каталогу | Сверка с каталогом |
| DS-TPL-12 | Нажать «Создать миссию» / перейти к проверкам | Подсветка шаблонов не подменяет отдельные planning- и safety-gates | Проверка перехода |

### 9.3 Разделение макета и рабочей логики

- **Qt Design Studio / QML:** компоновка, состояния элементов, раскрытие группы дополнительных шаблонов, интерактивность демонстрационного сценария.
- **Task interpretation:** извлечение намерения и параметров из текста, оценка неоднозначности и недостающих данных.
- **Template resolver:** выбор одного или нескольких шаблонов и объяснение причин выбора.
- **Mission planner / Safety:** построение миссии и независимые проверки допустимости.

Не реализовывать распознавание задачи, планирование или safety-решения внутри визуального макета как отдельную конкурирующую логику. HMI отображает состояние, полученное от соответствующих компонентов.

### 9.4 Текущий статус проверки

Требования и матрица проверки зафиксированы. Фактическую проверку QML в Qt Design Studio необходимо выполнить на актуальном файле проекта. В доступном репозитории BlueSkyPro сейчас опубликованы документы и алгоритмические материалы, но не обнаружены файлы Qt Design Studio/QML; поэтому утверждать, что макет уже изменён или тесты пройдены, нельзя.

Для завершения проверки:
1. открыть актуальный проект BlueSkyPRO-HMI в Qt Design Studio;
2. реализовать/проверить состояния на существующих элементах библиотеки, не меняя общую компоновку без необходимости;
3. прогнать DS-TPL-01…DS-TPL-12;
4. сохранить снимки состояний и записать результат по каждому ID;
5. внести QML и результаты проверки в соответствующую ветку Git и выполнить повторную проверку после коммита.
