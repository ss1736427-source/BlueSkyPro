# PROJECT RULES

## 1. Назначение

Этот файл содержит накопленные правила работы над проектом.

Правила применяются при последующей работе с документацией, структурой и материалами проекта.

---

## 2. Накопление правил

- Каждое новое правило, явно согласованное в работе над проектом, добавляется в этот файл.
- Новые правила не должны молча заменять ранее установленные.
- При противоречии между правилами необходимо сначала выявить противоречие и согласовать его.
- Перед существенным изменением документации необходимо учитывать действующие правила из этого файла.

---

## 3. Материалы проекта

- Переданный пользователем материал является исходным материалом проекта.
- Материалы, предназначенные для проекта, должны сохраняться в Obsidian в соответствующих документах.
- Переписка не является заменой сохранённому материалу проекта.
- При необходимости принятия решения необходимо обращаться к соответствующим материалам проекта.
- Терминология, структура и логика существующей документации должны сохраняться, если пользователь явно не поручил их изменить.
- Нельзя молча заменять содержание проекта общими знаниями или собственными предположениями.

---

## 4. Изменение документации

Основной принцип:

**изменение → проверка → сохранение проверенной версии**

После каждого существенного изменения:

1. определить, что именно изменяется;
2. изменить только необходимое;
3. выполнить проверку;
4. убедиться, что подтверждённые ошибки устранены;
5. сохранить проверенную версию;
6. использовать её как новую контрольную версию.

---

## 5. Грамматика и текстовые повреждения

- Цель текстовой очистки — чистота грамматики и корректность документации.
- Не выполнять широкие автоматические замены без контекстной проверки.
- Не исправлять нормальный текст только потому, что отдельное слово совпадает с шаблоном ошибки.
- Автоматически исправлять только подтверждённые типы повреждений.
- Перед массовым исправлением сначала выполнять диагностический проход.
- Диагностический проход не должен изменять Markdown-файлы.
- После исправления выполнять повторную диагностику.
- Исправление считается завершённым только после прохождения контрольной проверки.

---

## 6. Известное буквенное повреждение

В документации ранее были выявлены два основных типа повреждений:

### 6.1. Потеря первой буквы

Примеры:

- `ри` → `При`
- `ля` → `Для`
- `еред` → `Перед`
- `осле` → `После`
- `сли` → `Если`
- `зменение` → `Изменение`
- `аршрут` → `Маршрут`
- `стальные` → `Остальные`
- `олученные` → `Полученные`
- `отовность` → `Готовность`
- `езультат` → `Результат`
- `анные` → `Данные`
- `ричина` → `Причина`
- `тклонение` → `Отклонение`
- `отеря` → `Потеря`
- `ерсональный` → `Персональный`
- `бщий` → `Общий`
- `рофиль` → `Профиль`

### 6.2. Повторение или смешение первой буквы

Примеры:

- `ССистема` → `Система`
- `сСистема` → `система`
- `ССистемы` → `Системы`
- `сСистемы` → `системы`
- `ССистемой` → `Системой`
- `сСистемой` → `системой`
- `ССистеме` → `Системе`
- `сСистеме` → `системе`
- `дДолжен` → `должен`
- `дДолжна` → `должна`
- `дДолжно` → `должно`
- `дДолжны` → `должны`
- `пПосле` → `После`
- `пПри` → `При`
- `дДля` → `Для`
- `пПилот` → `Пилот`

Эти шаблоны считаются известными повреждениями и должны проверяться в последующих текстовых проверках.

---

## 7. Контрольная версия

После завершённой очистки известного буквенного повреждения была выполнена контрольная диагностика.

Результат:

**0 известных повреждений.**

Текущая версия является контрольной точкой для дальнейшей работы.

---

## 8. Backup

Перед массовым изменением рабочих Markdown-файлов необходимо создавать backup текущего состояния.

Backup должен:

- содержать исходные версии изменяемых файлов;
- находиться отдельно от рабочих файлов;
- позволять восстановить состояние до операции;
- не использоваться как рабочая документация.

---

## 9. Диагностика

Предпочтительный принцип:

**один диагностический проход → один отчёт → анализ результата → один контролируемый проход исправления → повторная диагностика**

Нельзя выполнять многократные хаотические исправления одного и того же повреждения.

Если диагностика даёт неожиданный результат, исправление останавливается до понимания причины.

---

## 10. Сохранение

- Проверенная версия должна сохраняться после завершения соответствующего прохода.
- Формат Markdown должен сохраняться.
- Кодировка рабочих текстовых файлов: UTF-8 без BOM.
- После сохранения необходимо проверять результат чтением файла или отдельной диагностикой.

---

## 11. Запрет на слепое исправление

Запрещается:

- выполнять массовую замену распространённых слов без контекста;
- заменять `при`, `для`, `после`, `пилот`, `должен` и подобные нормальные слова только по совпадению;
- переписывать документ целиком ради исправления одной ошибки;
- считать отсутствие результатов одного диагностического шаблона доказательством полной грамматической безошибочности;
- изменять содержание документа под видом грамматической очистки.

---

## 12. Статус грамматической проверки

Проверка известных повреждений и общая проверка грамматики — разные задачи.

Результат:

**0 известных повреждений**

означает отсутствие ранее определённых типов повреждения.

Это не означает автоматически отсутствие всех орфографических и грамматических ошибок.

Для утверждения о полной грамматической проверке требуется отдельный грамматический анализ и проверка его результатов.

---

## Mandatory project work order

- WORK ORDER RULE: Before starting any new project task, determine its position in [[PROJECT_WORK_ORDER]]. Follow the sequence defined there. Do not skip stages. Any change to the work order must be documented as a project decision and reflected in the project rules.



## Autonomous continuation rule

When the current work order defines the next step and no action, decision, approval, clarification, or external input is required from the user, work shall continue automatically through the next defined steps. The assistant shall not stop and request a new command merely to advance the established sequence.

The assistant shall pause only when user participation is actually required, including for:
- an explicit decision or approval;
- missing project-specific information that cannot be established from the controlled knowledge base;
- a required physical/local operation on the user's system;
- a safety, certification, scope, or configuration decision that must be made by the user.

This rule is subordinate to the fixed project work order and existing project rules and shall be applied together with them.

## 14. Эффективность технических итераций

Для технических и визуальных задач действует принцип **«диагностика прежде итерации»**.

Перед исправлением необходимо:
1. зафиксировать эталонный результат и фактическое текущее состояние;
2. определить измеримую причину отклонения;
3. внести минимально необходимое изменение;
4. проверить результат объективным способом;
5. только после подтверждения результата считать итерацию завершённой.

Запрещается последовательно выполнять серию предположительных исправлений одной и той же проблемы без установления причины.

Если первое исправление не устранило проблему, следующий шаг должен начинаться с повторной диагностики, а не с очередного предположительного изменения.

Для элементарных задач не допускается неоправданное накопление множества мелких коммитов. Если число итераций быстро растёт, работа должна быть остановлена для пересмотра диагностического подхода и поиска первопричины.

Цель: **минимальное число контролируемых итераций при сохранении полной проверяемости результата**.
