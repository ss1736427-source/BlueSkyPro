# BlueSky PRO — GitHub Development Protocol

## 1. Назначение

Этот протокол устанавливает единый порядок работы с GitHub для разработки, проверки и сохранения изменений BlueSky PRO.

Цель: минимизировать повторные действия, исключить работу с устаревшим состоянием репозитория и не считать изменение проверенным до подтверждения именно той версии, которая находится в `main`.

## 2. Основной принцип

Работа выполняется по цепочке:

```text
текущее состояние main
→ анализ
→ минимальное изменение
→ тест
→ commit
→ проверка diff
→ CI именно этого commit
→ подтверждённая версия
→ следующий шаг
```

Если следующий шаг однозначен и не требует архитектурного решения пользователя, работа продолжается автоматически.

## 3. Что проверяется перед изменением

1. Текущий `HEAD` ветки `main`.
2. Состояние изменяемых файлов.
3. Связанные тесты и CMake/сборочная конфигурация.
4. Последний подтверждённый CI.
5. Наличие уже выполненного изменения, чтобы не создавать дубликат.

Запрещено основывать новое изменение на предположении о текущем `main`.

## 4. Что считается необходимым изменением

Изменяется только то, что требуется для закрытия конкретного дефекта, требования или проверки.

Не допускается:

- рефакторинг без необходимости для текущей задачи;
- изменение публичного поведения без отдельного решения;
- изменение соседних модулей только ради удобства;
- создание дубликата уже существующего controlled record;
- замена существующего требования новым без отдельного решения.

## 5. Группировка изменений

Связанные изменения объединяются в один логический пакет, если это не ухудшает трассируемость.

Пример:

```text
изменение контракта
+ реализация
+ тест
+ CMake
→ один логический commit
→ один CI
```

Мелкие независимые изменения не объединяются искусственно.

## 6. Контроль SHA

SHA commit является главным идентификатором проверяемой версии.

После каждого commit необходимо установить:

```text
BASE SHA
→ NEW SHA
```

Затем проверить, что CI относится именно к `NEW SHA`.

## 7. Правило CI

Статус считается подтверждённым только если одновременно совпадают:

- repository;
- branch (`main`, если работа ведётся в main);
- `head_sha` CI;
- ожидаемый commit;
- результат Build;
- результат Test.

Если CI относится к предыдущему commit, он не подтверждает текущий.

Если CI отсутствует, состояние считается **UNVERIFIED**, а не `PASS`.

## 8. Повторная проверка

Если CI не появился автоматически:

1. проверить trigger workflow;
2. проверить `head_sha` текущего `main`;
3. проверить наличие workflow run для этого SHA;
4. не выдавать предыдущий успешный run за текущий;
5. не вносить новые изменения только для создания видимости активности CI.

Если доступный интерфейс не позволяет запустить workflow вручную, это фиксируется как ограничение проверки.

## 9. Тестовый принцип

Для каждого критического правила должен существовать проверяемый сценарий.

Минимальная цепочка:

```text
требование
→ реализация
→ негативный сценарий
→ позитивный сценарий
→ CI
```

Особое внимание уделяется safety-critical и hard-constraint логике.

## 10. Контрольные точки

Логический блок считается закрытым только после проверки:

- логики;
- интеграции между слоями;
- тестов;
- соответствия исходному требованию;
- CI для соответствующего SHA.

Формат:

```text
CHECKPOINT <ID> — CLOSED
```

До закрытия контрольной точки результат не объявляется окончательно проверенным.

## 11. Правило автоматического продолжения

Команда пользователя `go` означает:

> Продолжить работу с текущего подтверждённого состояния, найти следующий необходимый шаг, выполнить его, проверить результат и остановиться только при необходимости решения пользователя.

**Не требовать повторного `go` между техническими шагами.** Если следующий шаг однозначен и не требует решения пользователя, исполнитель продолжает выполнение без запроса пользователя.

Если среда выполнения поддерживает автоматический запуск нового рабочего цикла после завершения текущего, такой цикл может быть запущен через 5 секунд. Это не является обязательным механизмом протокола: при отсутствии такой возможности работа продолжается в следующем доступном рабочем цикле без необходимости повторного подтверждения со стороны пользователя.

## 12. Когда требуется решение пользователя

Работа останавливается только если требуется выбор, который нельзя безопасно вывести из утверждённых требований. Например:

- изменение архитектурного принципа;
- изменение утверждённого требования;
- изменение safety-ограничения;
- выбор между существенно различающимися вариантами поведения;
- принятие нормативного или продуктового решения.

В остальных случаях исполнитель сам выбирает следующий проверяемый шаг и продолжает работу.

## 13. Формат отчёта

После существенного шага сообщается кратко:

```text
Изменение: <что сделано>
Commit: <SHA>
Тест: PASS/FAIL
CI: PASS/FAIL/UNVERIFIED
Контрольная точка: OPEN/CLOSED
Следующий шаг: <что проверяется дальше>
```

Не использовать `PASS`, если соответствующее состояние фактически не подтверждено.

## 14. Запрет на потерю контекста

При переходе к следующему блоку сохраняются:

- последний подтверждённый SHA;
- незакрытые проверки;
- связанные требования;
- известные ограничения;
- причина следующего изменения.

Это предотвращает повторное исследование уже закрытых участков.

## 15. Безопасное правило остановки

Если состояние репозитория неоднозначно, SHA не совпадает, diff неясен, тест не найден или CI относится к другой версии — работа над следующим зависимым изменением не продолжается до восстановления однозначного состояния.

## 16. Правило постоянного обращения к протоколу

Перед каждым существенным изменением и перед переходом к следующему логическому блоку исполнитель обязан сверяться с этим протоколом и действующими правилами работы BlueSky PRO.

Протокол и правила работы являются постоянной рабочей опорой проекта и не должны игнорироваться из-за краткости команды пользователя (`go`, `делай`, `проверяй`, `go дальше` и аналогичных команд).

Если новое указание пользователя прямо изменяет это правило, приоритет имеет последнее явное указание пользователя, после чего протокол должен быть обновлён соответствующим образом.


## 17. Обязательный протокол действий AI-исполнителя

Этот раздел обязателен для ChatGPT и любого автоматизированного исполнителя, работающего с репозиторием. Он дополняет, а не заменяет предыдущие разделы.

### 17.1. Проверка состояния до работы

Перед каждой записью в GitHub исполнитель обязан заново проверить:

1. Полное имя репозитория: `ss1736427-source/BlueSkyPro`.
2. Текущую вершину `main` и выбранную рабочую ветку.
3. Открытый PR, если задача связана с уже начатой работой: его номер, head, base и последний head SHA.
4. SHA и содержимое каждого изменяемого файла.
5. Незавершённые CI-проверки и последние подтверждённые результаты.

Нельзя считать ветку, SHA, статус PR или содержимое файла актуальными только потому, что они упоминались ранее в чате. Если состояние не удалось подтвердить инструментально, это прямо указывается; запись не выполняется.

### 17.2. Выбор ветки и границы изменений

- `main` считается защищённой веткой. Исполнитель не записывает изменения непосредственно в `main`.
- Для новой самостоятельной задачи создаётся отдельная ветка от актуальной `main`, если пользователь явно не утвердил другую базу.
- Продолжая существующую задачу, исполнитель использует только проверенные head/base конкретного PR. Нельзя незаметно менять базовую ветку PR.
- Одна логическая задача — одна рабочая ветка и один PR, если нет обоснованной необходимости разделить работу.
- Нельзя объединять PR, закрывать его, менять его целевую ветку или выполнять force-push без явного разрешения пользователя.
- До изменения фиксируются цель, разрешённые файлы и критерии приёмки. Посторонние изменения в задачу не включаются.

### 17.3. Проверка источника истины

Перед редактированием исполнитель определяет, какой файл или инструмент является утверждённым источником истины для соответствующей части проекта.

Для HMI BlueSky PRO источником истины являются проект и файлы Qt Design Studio. Нельзя подменять утверждённую работу в Qt Design Studio прямым редактированием QML через GitHub, восстанавливать отдельные старые файлы или переносить состояние из устаревшей копии без явного указания пользователя и проверки согласованности.

Git используется для контроля версий, CMake/Ninja — для сборки. Локальную рабочую копию необходимо сверять с соответствующей удалённой веткой до изменений. Репозиторий `BlueSky-PRO-Knowledge` не является текущим источником HMI.

### 17.4. Безопасное редактирование

Перед записью исполнитель обязан прочитать полный актуальный файл и проверить связанные компоненты, вызовы, свойства, сигналы, тесты и конфигурацию.

- Изменять только минимально необходимый объём.
- Использовать актуальный blob SHA файла при обновлении через GitHub API.
- Не выполнять параллельные записи в один и тот же файл.
- Не заменять полный файл фрагментом и не восстанавливать его из памяти или старого сообщения.
- Не дублировать существующие требования, тестовые записи или документацию без проверки.
- Не помещать ключи API, пароли, токены и другие секреты в код, документацию, коммиты или логи. При обнаружении секрета не повторять его в отчёте.
- Если diff неожиданно затрагивает несвязанные строки или файлы, остановить запись и выяснить причину.

### 17.5. Контроль после записи

После каждого изменения исполнитель обязан:

1. Повторно прочитать изменённый файл из целевой ветки.
2. Проверить фактический diff относительно родительского состояния.
3. Проверить формат, ссылки, кодировку, синтаксис и связанные зависимости в пределах доступных средств.
4. Убедиться, что новый коммит находится в ожидаемой ветке и что PR указывает на правильные head/base.
5. Запустить или проверить доступные автоматические проверки для точного нового SHA.
6. Отдельно отметить проверки, которые требуют запуска приложения или аппаратуры на ПК пользователя.

Наличие коммита не означает, что изменение исправно. Успешный CI предыдущего SHA не подтверждает новый SHA. Если проверка не запускалась или её результат недоступен, статус — `UNVERIFIED`, а не `PASS`.

### 17.6. Коммиты и Pull Request

- Коммит создаётся после проверки diff и должен иметь конкретное, правдивое сообщение о содержимом.
- Не объединять независимые изменения в один коммит без необходимости.
- PR по умолчанию создаётся как Draft, пока критерии приёмки и необходимые проверки не подтверждены.
- В описании PR указываются цель, изменённые файлы, базовый и новый SHA, проведённые проверки, результаты и оставшиеся ограничения.
- Исполнитель не выполняет merge без отдельного явного разрешения пользователя, даже если все проверки прошли.
- Если в ходе проверки обнаружен дефект, сначала устанавливается его причина и затронутый коммит; не добавлять случайные исправления поверх неизвестного состояния.

### 17.7. Обязательный формат отчёта

После каждого существенного этапа исполнитель сообщает:

```text
Задача:
Репозиторий:
Рабочая ветка:
Целевая ветка:
PR:
BASE SHA:
NEW SHA:
Изменённые файлы:
Diff проверен: YES/NO
Тесты: PASS/FAIL/UNVERIFIED
CI для NEW SHA: PASS/FAIL/IN_PROGRESS/UNVERIFIED
Проверка на ПК пользователя требуется: YES/NO
Ограничения и риски:
Следующий шаг:
Merge выполнен: NO (до отдельного разрешения пользователя)
```

Не указывать несуществующие результаты тестов, не утверждать, что файл или PR изменён, пока инструмент не подтвердил операцию, и не выдавать предположение за факт.

### 17.8. Обработка неоднозначности и ошибок

Если обнаружены разные версии файла, неизвестная база, конфликт веток, непредвиденный diff, неожиданный результат API или несовпадение SHA:

1. Прекратить дальнейшие зависимые записи.
2. Повторно получить актуальное состояние GitHub.
3. Определить последний достоверный SHA и точку расхождения.
4. Сообщить пользователю о фактах и рисках.
5. Продолжать только после восстановления однозначного состояния; запросить решение пользователя, если требуется выбор с последствиями для архитектуры или данных.

### 17.9. Приоритет правил

Приоритет имеют: явные последние указания пользователя, требования безопасности и утверждённые проектные ограничения, затем настоящий протокол и локальные инструкции соответствующего модуля. Если новое указание противоречит протоколу, исполнитель не должен молча выбирать трактовку: он фиксирует противоречие и запрашивает решение, когда последствия существенны.
