# BlueSky PRO — GitHub Development Protocol

## 1. Назначение

Этот протокол устанавливает единый порядок работы с GitHub для разработки, проверки и сохранения изменений BlueSky PRO.

Цель: минимизировать повторные действия, исключить работу с устаревшим состоянием репозитория и не считать изменение проверенным до подтверждения именно той версии, которая находится в `main`.

## 2. Основной принцип

Работа выполняется по цепочке:

```text
текущее состояние main
→ анализ
→ минимальное изменение
→ тест
→ commit
→ проверка diff
→ CI именно этого commit
→ подтверждённая версия
→ следующий шаг
```

Если следующий шаг однозначен и не требует архитектурного решения пользователя, работа продолжается автоматически.

## 3. Что проверяется перед изменением

1. Текущий `HEAD` ветки `main`.
2. Состояние изменяемых файлов.
3. Связанные тесты и CMake/сборочная конфигурация.
4. Последний подтверждённый CI.
5. Наличие уже выполненного изменения, чтобы не создавать дубликат.

Запрещено основывать новое изменение на предположении о текущем `main`.

## 4. Что считается необходимым изменением

Изменяется только то, что требуется для закрытия конкретного дефекта, требования или проверки.

Не допускается:

- рефакторинг без необходимости для текущей задачи;
- изменение публичного поведения без отдельного решения;
- изменение соседних модулей только ради удобства;
- создание дубликата уже существующего controlled record;
- замена существующего требования новым без отдельного решения.

## 5. Группировка изменений

Связанные изменения объединяются в один логический пакет, если это не ухудшает трассируемость.

Пример:

```text
изменение контракта
+ реализация
+ тест
+ CMake
→ один логический commit
→ один CI
```

Мелкие независимые изменения не объединяются искусственно.

## 6. Контроль SHA

SHA commit является главным идентификатором проверяемой версии.

После каждого commit необходимо установить:

```text
BASE SHA
→ NEW SHA
```

Затем проверить, что CI относится именно к `NEW SHA`.

## 7. Правило CI

Статус считается подтверждённым только если одновременно совпадают:

- repository;
- branch (`main`, если работа ведётся в main);
- `head_sha` CI;
- ожидаемый commit;
- результат Build;
- результат Test.

Если CI относится к предыдущему commit, он не подтверждает текущий.

Если CI отсутствует, состояние считается **UNVERIFIED**, а не `PASS`.

## 8. Повторная проверка

Если CI не появился автоматически:

1. проверить trigger workflow;
2. проверить `head_sha` текущего `main`;
3. проверить наличие workflow run для этого SHA;
4. не выдавать предыдущий успешный run за текущий;
5. не вносить новые изменения только для создания видимости активности CI.

Если доступный интерфейс не позволяет запустить workflow вручную, это фиксируется как ограничение проверки.

## 9. Тестовый принцип

Для каждого критического правила должен существовать проверяемый сценарий.

Минимальная цепочка:

```text
требование
→ реализация
→ негативный сценарий
→ позитивный сценарий
→ CI
```

Особое внимание уделяется safety-critical и hard-constraint логике.

## 10. Контрольные точки

Логический блок считается закрытым только после проверки:

- логики;
- интеграции между слоями;
- тестов;
- соответствия исходному требованию;
- CI для соответствующего SHA.

Формат:

```text
CHECKPOINT <ID> — CLOSED
```

До закрытия контрольной точки результат не объявляется окончательно проверенным.

## 11. Правило автоматического продолжения

Команда пользователя `go` означает:

> Продолжить работу с текущего подтверждённого состояния, найти следующий необходимый шаг, выполнить его, проверить результат и остановиться только при необходимости решения пользователя.

**Не требовать повторного `go` между техническими шагами.** Если следующий шаг однозначен и не требует решения пользователя, исполнитель продолжает выполнение без запроса пользователя.

Если среда выполнения поддерживает автоматический запуск нового рабочего цикла после завершения текущего, такой цикл может быть запущен через 5 секунд. Это не является обязательным механизмом протокола: при отсутствии такой возможности работа продолжается в следующем доступном рабочем цикле без необходимости повторного подтверждения со стороны пользователя.

## 12. Когда требуется решение пользователя

Работа останавливается только если требуется выбор, который нельзя безопасно вывести из утверждённых требований. Например:

- изменение архитектурного принципа;
- изменение утверждённого требования;
- изменение safety-ограничения;
- выбор между существенно различающимися вариантами поведения;
- принятие нормативного или продуктового решения.

В остальных случаях исполнитель сам выбирает следующий проверяемый шаг и продолжает работу.

## 13. Формат отчёта

После существенного шага сообщается кратко:

```text
Изменение: <что сделано>
Commit: <SHA>
Тест: PASS/FAIL
CI: PASS/FAIL/UNVERIFIED
Контрольная точка: OPEN/CLOSED
Следующий шаг: <что проверяется дальше>
```

Не использовать `PASS`, если соответствующее состояние фактически не подтверждено.

## 14. Запрет на потерю контекста

При переходе к следующему блоку сохраняются:

- последний подтверждённый SHA;
- незакрытые проверки;
- связанные требования;
- известные ограничения;
- причина следующего изменения.

Это предотвращает повторное исследование уже закрытых участков.

## 15. Безопасное правило остановки

Если состояние репозитория неоднозначно, SHA не совпадает, diff неясен, тест не найден или CI относится к другой версии — работа над следующим зависимым изменением не продолжается до восстановления однозначного состояния.

## 16. Правило постоянного обращения к протоколу

Перед каждым существенным изменением и перед переходом к следующему логическому блоку исполнитель обязан сверяться с этим протоколом и действующими правилами работы BlueSky PRO.

Протокол и правила работы являются постоянной рабочей опорой проекта и не должны игнорироваться из-за краткости команды пользователя (`go`, `делай`, `проверяй`, `go дальше` и аналогичных команд).

Если новое указание пользователя прямо изменяет это правило, приоритет имеет последнее явное указание пользователя, после чего протокол должен быть обновлён соответствующим образом.
