# BlueSky PRO — Правила работы

## 0. Обязательный алгоритм начала и продолжения работы

Перед каждым существенным рабочим шагом исполнитель начинает с этого алгоритма. Он является операционным алгоритмом выполнения, а не предложением пользователю подтвердить следующий шаг.

```text
READ CURRENT STATE
→ READ / APPLY THIS ALGORITHM
→ READ GOVERNING PROTOCOL
→ READ CURRENT WORK PACKAGE
→ READ CHECKPOINTS / REQUIREMENTS / RELEVANT HISTORY
→ IDENTIFY CURRENT STATE
→ IDENTIFY NEXT DETERMINISTIC STEP
→ CHECK BLOCKERS / PREREQUISITES
→ EXECUTE MINIMAL REQUIRED CHANGE
→ VERIFY CHANGE
→ COMMIT TO GITHUB
→ VERIFY NEW COMMIT / DIFF / TESTS / CI AS APPLICABLE
→ RESTART THIS ALGORITHM FROM THE BEGINNING
→ DETERMINE NEXT STEP
→ IF DETERMINISTIC: CONTINUE AUTOMATICALLY
→ IF USER DECISION REQUIRED: STOP AND STATE EXACT DECISION
```

### Правила алгоритма

1. **Не ждать `GO` между детерминированными шагами.** Команда `go` означает продолжить текущую работу, но не является обязательным разрешением на каждый следующий шаг.
2. **Продолжать автоматически**, пока следующий шаг однозначно определяется утверждёнными требованиями, протоколами, архитектурой и текущим состоянием репозитория.
3. **Останавливаться только при genuine user decision** — когда решение нельзя надёжно вывести из зафиксированных материалов.
4. **Если этап заблокирован обязательной зависимостью**, самостоятельно переключиться на минимальный этап, устраняющий blocker, выполнить его и вернуться к исходной последовательности.
5. **Не создавать новый артефакт, если уже существует подходящий.** Сначала использовать или минимально обновить существующий controlled record.
6. **Не делать серьёзных переделок без объективной необходимости.** Каждый шаг должен формировать устойчивую основу следующего этапа.
7. **При отсутствии данных реальных испытаний создавать controlled stub**, продолжать доступную работу и не выдавать stub за evidence.
8. **После реальных испытаний заменить stub фактическими данными** и обновить связанную документацию, traceability и verification status только при наличии подтверждающего evidence.
9. **После каждого изменения переходить к следующей детерминированной проверке/работе**, а не возвращать управление пользователю без необходимости.
10. **После каждого commit в GitHub обязательно перезапускать алгоритм с самого начала.** Новый commit считается новым фактическим состоянием репозитория и не должен обрабатываться как продолжение старого состояния без повторного чтения алгоритма, governing protocol, текущего work package, checkpoints, requirements и relevant history.
11. **Автономное продолжение должно быть реальным, а не только текстовым правилом.** Если текущий сеанс не способен физически инициировать следующий рабочий шаг после завершения ответа, исполнитель не должен считать работу непрерывной. Для продолжения без пользовательского ввода используется доступный механизм фонового/планируемого запуска; каждый такой запуск обязан начать алгоритм заново и выполнить доступный детерминированный рабочий шаг. Если механизм имеет ограничение по частоте, применяется максимально доступная частота, а не обещается недоступный интервал.
12. **Желаемая периодичность автономного запуска — 1 минута.** Автономный рабочий цикл должен инициироваться не реже одного раза в минуту, когда среда выполнения поддерживает такую частоту. Ограничение конкретного механизма исполнения не изменяет требование проекта; при техническом ограничении фактическая частота фиксируется как ограничение среды, а не как изменение рабочего правила.

### Правило изменения алгоритма

Если в проекте появляется новое постоянное рабочее правило, которое изменяет способ выполнения работы, исполнитель обязан:

```text
NEW WORKING RULE
→ ADD / MODIFY RULE IN THIS ALGORITHM
→ SAVE UPDATED RULES TO REPOSITORY
→ APPLY UPDATED ALGORITHM
→ CONTINUE WORK
```

То есть алгоритм всегда является актуальной версией рабочих правил. Новое постоянное правило не должно оставаться только в переписке.

## 1. Режим работы

Основной режим проекта — непрерывное выполнение работы без лишних запросов пользователю.

Команды `go`, `делай`, `продолжай`, `проверяй` и аналогичные короткие команды означают: продолжить с текущего состояния проекта по утверждённому протоколу.

Если следующий технический шаг однозначен и не требует решения пользователя, исполнитель выполняет его сам.

## 2. Автоматическое продолжение

После завершения технического шага не требуется повторная команда пользователя, если следующий шаг определён и безопасен.

Желаемая периодичность автоматического рабочего цикла — **1 минута**. Если доступный механизм исполнения не поддерживает запуск с таким интервалом, нельзя утверждать, что минутный цикл фактически обеспечен; необходимо явно зафиксировать техническое ограничение среды и использовать максимально доступную частоту.

Интервал запуска не является причиной запрашивать подтверждение пользователя.

## 3. Когда останавливаемся

Исполнитель останавливается только когда необходимо решение пользователя, которое нельзя надёжно вывести из зафиксированных требований.

К таким случаям относятся:

- изменение архитектурного принципа;
- изменение утверждённого продуктового требования;
- изменение safety-ограничения;
- выбор между существенно различающимися вариантами поведения;
- нормативное или юридически значимое решение;
- неоднозначность, которую невозможно устранить проверкой имеющихся материалов.

Во всех остальных случаях исполнитель продолжает работу самостоятельно.

## 4. Обязательная зависимость этапа

Если текущий этап невозможно корректно продолжать без завершения другого этапа, исполнитель не останавливает работу и не просит пользователя дать команду на переключение.

Исполнитель должен:

1. определить конкретную незавершённую зависимость;
2. зафиксировать её как блокирующую текущий этап;
3. переключиться на минимальный обязательный этап, завершение которого необходимо для продолжения;
4. выполнить все доступные детерминированные действия на этом этапе;
5. после устранения зависимости автоматически вернуться к исходному этапу.

Если обязательная зависимость сама требует решения пользователя, остановка производится только на этой точке и только по конкретному решению.

## 5. GitHub

Для работы с GitHub постоянно применяется `GITHUB_DEVELOPMENT_PROTOCOL.md`.

Перед существенным изменением проверяется актуальный `main` и связанные файлы. После изменения проверяются diff, тесты и CI именно для нового SHA.

Предыдущий успешный CI не считается подтверждением более нового commit.

## 6. Контекст проекта

При переходе между этапами сохраняются требования, принятые решения, незакрытые проверки, ограничения, текущую контрольную точку и последний подтверждённый SHA.

Нельзя повторно заставлять пользователя сообщать уже зафиксированные решения без объективной необходимости.

## 7. Минимализм изменений

Изменяется только необходимое для текущей задачи. Не допускаются ненужный рефакторинг, изменение уже утверждённого поведения или дублирование существующих решений.

## 8. Контроль качества

Технический шаг считается завершённым только после соответствующей проверки. Для критической логики используется цепочка:

```text
требование
→ реализация
→ тест
→ CI
→ контрольная точка
```

Неподтверждённое состояние явно обозначается как `UNVERIFIED`.

## 9. Заглушки до реальных испытаний

Если выполнение или проверка требуют данных реальных испытаний, а такие данные ещё отсутствуют, исполнитель создаёт controlled stub вместо остановки подготовительного этапа.

Stub:

- явно обозначается как временный и неиспытательный;
- не считается evidence;
- не даёт статуса `PASS`, `PASSED` или `VERIFIED`;
- содержит поля, которые будут заменены фактическими данными;
- должен быть удалён или заменён фактической записью после реального испытания.

После проведения реальных испытаний исполнитель обязан обновить соответствующую документацию фактическими результатами, evidence, конфигурацией, идентификаторами сборки/ревизии и review-данными. Статус `PASSED` / `VERIFIED` устанавливается только если реальные результаты действительно удовлетворяют применимым критериям.

## 10. Последовательность и отсутствие серьёзных переделок

Работа строится так, чтобы каждый завершённый этап формировал устойчивую основу для следующего этапа и не требовал возврата к уже завершённым уровням без объективной причины.

Перед реализацией проверяется наличие необходимого контракта предыдущего уровня. При отсутствии такого контракта сначала завершается обязательная зависимость по правилу раздела 4.

Предпочтение отдаётся интерфейсам, адаптерам, конфигурации и другим изолирующим механизмам, если они позволяют отложить решение без встраивания временного решения в устойчивую архитектуру.

## 11. Постоянное соблюдение правил

Эти правила и `GITHUB_DEVELOPMENT_PROTOCOL.md` являются постоянной рабочей основой проекта.

Исполнитель должен обращаться к ним перед существенными изменениями и переходами между логическими блоками, даже если команда пользователя состоит только из `go`.

Если пользователь явно изменяет правило работы, последнее явное указание пользователя имеет приоритет, после чего соответствующий документ обновляется.

## 12. Эффективность технических итераций

Для технических и визуальных задач применяется принцип **«диагностика прежде итерации»**.

Рабочая последовательность:

```text
ЭТАЛОН + ТЕКУЩЕЕ СОСТОЯНИЕ
→ ИЗМЕРИМАЯ ДИАГНОСТИКА
→ ОПРЕДЕЛЕНИЕ ПЕРВОПРИЧИНЫ
→ МИНИМАЛЬНОЕ ИЗМЕНЕНИЕ
→ ОБЪЕКТИВНАЯ ПРОВЕРКА
→ ЗАФИКСИРОВАННЫЙ РЕЗУЛЬТАТ
```

Нельзя выполнять серию предположительных исправлений одной и той же проблемы без повторной диагностики и установления причины.

Если первое исправление не устранило проблему, следующий шаг начинается с диагностики, а не с очередного предположительного фикса.

Для простых задач не допускается неоправданное накопление мелких итераций и коммитов. При быстром росте числа итераций работа должна быть остановлена для пересмотра диагностического подхода и поиска первопричины.

Цель: **минимальное число контролируемых итераций при полной проверяемости результата**.
