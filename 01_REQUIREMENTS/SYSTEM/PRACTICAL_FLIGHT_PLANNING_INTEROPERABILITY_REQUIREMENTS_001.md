# Practical Flight Planning Interoperability Requirements

## 1. Назначение

Документ фиксирует полезные для BlueSky PRO практические функции, выявленные при сопоставлении существующей архитектуры проекта с внешним практическим материалом GeoPlus.

Источник рассматривается как **практический внешний источник**, а не как нормативная или сертификационная база.

Источник:

`https://geoplys.ru/article/kak-vybrat-programmu-planirovaniya-polyotov-dlya-dronov/`

## 2. Результат сопоставления

Внешний материал выделяет шесть практических критериев выбора ПО планирования полётов:

1. совместимость;
2. надёжность;
3. многопользовательская работа;
4. универсальность;
5. офлайн-доступ;
6. поддержка загрузки KML.

В BlueSky PRO первые четыре направления уже представлены существующими архитектурными решениями. Наиболее полезными дополнениями являются формализация offline-first, межустройственной синхронизации и KML interoperability.

## 3. Что не нужно создавать заново

Следующие возможности не должны порождать отдельные подсистемы, если они уже покрываются существующей архитектурой:

- поддержка различных БПЛА — через модель конфигурации и совместимости;
- многопользовательская работа — через Administrator / Engineer / Technician / Pilot;
- назначение пилота и оборудования — через существующую модель ролей и конфигурации;
- единый контур подготовки и выполнения — через существующие Flight Planning / Flight решения;
- автономная работа бортов — через существующую архитектуру навигации, C2 и safety;
- внешняя техническая эксплуатация — через Integration Layer, без создания собственной MRO-системы;
- внешняя обработка результатов — через существующую архитектуру внешней обработки данных.

## 4. Кандидатные требования

### PFP-REQ-001 — Offline Mission Package

BlueSky PRO должна обеспечивать сохранение подготовленного плана миссии и необходимых для его выполнения данных на локальном устройстве до начала выполнения.

Минимальный offline package должен включать только данные, необходимые для соответствующей миссии, включая план маршрута, параметры задания, назначенный БПЛА, необходимые ограничения и доступные офлайн-картографические данные.

### PFP-REQ-002 — Offline Continuity

При временной потере интернет-соединения BlueSky PRO не должна прекращать доступ к ранее подготовленному локальному плану и связанным с ним рабочим данным, если это не противоречит отдельным safety/C2 ограничениям.

### PFP-REQ-003 — Local Result Retention

Результаты завершённой миссии, сформированные на устройстве при отсутствии связи, должны сохраняться локально до возможности их контролируемой синхронизации.

### PFP-REQ-004 — Synchronization State

BlueSky PRO должна отображать пользователю состояние синхронизации только там, где оно влияет на дальнейшее действие:

- синхронизировано;
- ожидает передачи;
- требуется обновление;
- конфликт;
- ошибка;
- данные недоступны.

### PFP-REQ-005 — Controlled Synchronization

Синхронизация между рабочими местами и/или HUB должна использовать версию данных, идентификатор объекта и время изменения, обеспечивая возможность определить актуальную версию и обнаружить конфликт.

Конкретный механизм разрешения конфликтов определяется отдельным design document.

### PFP-REQ-006 — KML Import

BlueSky PRO должна предусматривать импорт KML как внешний источник геометрии задания.

Импортируемая геометрия должна проходить предварительную проверку до включения в план миссии.

### PFP-REQ-007 — KML Import Preview

Перед применением импортированного KML BlueSky PRO должна показывать пользователю краткий предварительный результат:

- тип геометрии;
- количество объектов/точек;
- область покрытия;
- координатную систему/признак корректности координат, если определяется;
- потенциальные ошибки или неподдерживаемые элементы.

Пользователь должен явно подтвердить применение импортированных данных.

### PFP-REQ-008 — Geometry-to-Mission Separation

Импорт геометрии не должен автоматически означать разрешение на выполнение полёта.

Путь обработки:

```text
KML
 ↓
IMPORT
 ↓
VALIDATION
 ↓
PREVIEW
 ↓
MISSION PLANNING
 ↓
SAFETY / READINESS CHECK
 ↓
EXECUTION
```

Это сохраняет существующую цепочку `MISSION → VALIDATION → READINESS → SAFETY GATE → OPERATOR APPROVAL → EXECUTION`.

### PFP-REQ-009 — Repeatable Mission Basis

BlueSky PRO должна позволять использовать ранее выполненную/сохранённую миссию как основу для повторного задания без необходимости создавать маршрут заново.

Перед повторным выполнением должны заново проверяться актуальные условия, ограничения, техническая готовность и иные изменяемые параметры.

### PFP-REQ-010 — Mission Revision After Task Change

При изменении исходных параметров задания BlueSky PRO должна позволять пересчитать затронутую часть маршрута без необоснованного ручного повторения всей процедуры планирования.

Изменение не должно обходить обязательные проверки и должно сохраняться как новая версия плана.

### PFP-REQ-011 — Mission / Pilot / Equipment Context

Назначение БПЛА, пилота и оборудования должно выполняться в контексте конкретной миссии и не требовать перехода в несвязанные административные разделы, если пользователь уже обладает необходимыми правами.

### PFP-REQ-012 — Contextual Information Display

Функции offline, synchronization, import и revision не должны перегружать основной экран планирования.

Информация и команды должны выводиться контекстно:

- постоянно — только то, что необходимо для текущей операции;
- второстепенное — в компактном подменю;
- состояние — через внешние индикаторы там, где этого достаточно;
- подробности — по запросу пользователя.

## 5. Offline maps

Внешняя практика показывает, что для реальной работы без связи недостаточно только хранить файл миссии: необходимы заранее подготовленные картографические данные. В Mission Planner, например, предусмотрено предварительное получение участков карт для offline использования. citeturn0search0turn0search4

Поэтому offline-картография рассматривается как часть `PFP-REQ-001`, а не как отдельная карта/подсистема.

Требование не устанавливает конкретного поставщика карт.

## 6. KML: граница применения

KML следует использовать как interoperability mechanism, а не как внутренний формат всего планировщика.

Допустимый сценарий:

```text
External GIS / KML
       ↓
   KML Import
       ↓
   Validation
       ↓
  Flight Chart
       ↓
 Mission Generator
```

Практические GCS также поддерживают загрузку/сохранение KML и использование импортированной геометрии при подготовке survey/grid missions. citeturn0search0turn0search12

## 7. Многобортный контекст

Для BlueSky PRO уже существующая многобортная архитектура должна использовать те же принципы:

- единый идентификатор миссии;
- отдельная конфигурация каждого БПЛА;
- независимое состояние каждого борта;
- возможность сравнения/просмотра нескольких БПЛА;
- контролируемая синхронизация;
- отсутствие необходимости дублировать одну и ту же операцию вручную для каждого борта, где это безопасно и допустимо.

Практические наземные станции также используют multi-vehicle представление и отдельные идентификаторы активных/неактивных аппаратов. citeturn0search13

## 8. Безопасностная граница

Ни один из настоящих candidate requirements не изменяет safety authority model.

Offline, KML, repeat mission, synchronization и automatic revision являются средствами подготовки/обмена данными и не имеют права самостоятельно разрешать выполнение полёта.

При конфликте:

```text
SAFETY
>
MANDATORY CONSTRAINTS
>
MISSION REQUIREMENTS
>
USER PREFERENCES
>
OPTIMIZATION
```

## 11. Заключение

В проект добавляются не все функции, перечисленные внешним источником, а только те, которые имеют практическую ценность для BlueSky PRO и не противоречат уже принятой архитектуре.

Основные добавления:

**offline continuity + local retention + synchronization state + controlled synchronization + KML interoperability + repeatable mission + controlled mission revision**, при сохранении минималистичного интерфейса и существующей safety authority chain.
