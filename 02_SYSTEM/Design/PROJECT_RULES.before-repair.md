# PROJECT RULES

## 1. азначение

тот файл содержит накопленные правила работы над проектом.

равила применяются при последующей работе с документацией, структурой и материалами проекта.

---

## 2. акопление правил

- аждое новое правило, явно согласованное в работе над проектом, добавляется в этот файл.
- овые правила не должны молча заменять ранее установленные.
- ри противоречии между правилами необходимо сначала выявить противоречие и согласовать его.
- еред существенным изменением документации необходимо учитывать действующие правила из этого файла.

---

## 3. атериалы проекта

- ереданный пользователем материал является исходным материалом проекта.
- атериалы, предназначенные для проекта, должны сохраняться в Obsidian в соответствующих документах.
- ереписка не является заменой сохранённому материалу проекта.
- ри необходимости принятия решения необходимо обращаться к соответствующим материалам проекта.
- Терминология, структура и логика существующей документации должны сохраняться, если пользователь явно не поручил их изменить.
- ельзя молча заменять содержание проекта общими знаниями или собственными предположениями.

---

## 4. зменение документации

сновной принцип:

**изменение → проверка → сохранение проверенной версии**

осле каждого существенного изменения:

1. определить, что именно изменяется;
2. изменить только необходимое;
3. выполнить проверку;
4. убедиться, что подтверждённые ошибки устранены;
5. сохранить проверенную версию;
6. использовать её как новую контрольную версию.

---

## 5. рамматика и текстовые повреждения

- Цель текстовой очистки — чистота грамматики и корректность документации.
- е выполнять широкие автоматические замены без контекстной проверки.
- е исправлять нормальный текст только потому, что отдельное слово совпадает с шаблоном ошибки.
- втоматически исправлять только подтверждённые типы повреждений.
- еред массовым исправлением сначала выполнять диагностический проход.
- иагностический проход не должен изменять Markdown-файлы.
- осле исправления выполнять повторную диагностику.
- справление считается завершённым только после прохождения контрольной проверки.

---

## 6. звестное буквенное повреждение

 документации ранее были выявлены два основных типа повреждений:

### 6.1. отеря первой буквы

римеры:

- `ри` → `ри`
- `ля` → `ля`
- `еред` → `еред`
- `осле` → `осле`
- `сли` → `сли`
- `зменение` → `зменение`
- `аршрут` → `аршрут`
- `стальные` → `стальные`
- `олученные` → `олученные`
- `отовность` → `отовность`
- `езультат` → `езультат`
- `анные` → `анные`
- `ричина` → `ричина`
- `тклонение` → `тклонение`
- `отеря` → `отеря`
- `ерсональный` → `ерсональный`
- `бщий` → `бщий`
- `рофиль` → `рофиль`

### 6.2. овторение или смешение первой буквы

римеры:

- `ССистема` → `Система`
- `сСистема` → `система`
- `ССистемы` → `Системы`
- `сСистемы` → `системы`
- `ССистемой` → `Системой`
- `сСистемой` → `системой`
- `ССистеме` → `Системе`
- `сСистеме` → `системе`
- `должен` → `должен`
- `должна` → `должна`
- `должно` → `должно`
- `должны` → `должны`
- `после` → `осле`
- `при` → `ри`
- `для` → `ля`
- `пилот` → `илот`

ти шаблоны считаются известными повреждениями и должны проверяться в последующих текстовых проверках.

---

## 7. онтрольная версия

осле завершённой очистки известного буквенного повреждения была выполнена контрольная диагностика.

езультат:

**0 известных повреждений.**

Текущая версия является контрольной точкой для дальнейшей работы.

---

## 8. Backup

еред массовым изменением рабочих Markdown-файлов необходимо создавать backup текущего состояния.

Backup должен:

- содержать исходные версии изменяемых файлов;
- находиться отдельно от рабочих файлов;
- позволять восстановить состояние до операции;
- не использоваться как рабочая документация.

---

## 9. иагностика

редпочтительный принцип:

**один диагностический проход → один отчёт → анализ результата → один контролируемый проход исправления → повторная диагностика**

ельзя выполнять многократные хаотичные исправления одного и того же повреждения.

сли диагностика даёт неожиданный результат, исправление останавливается до понимания причины.

---

## 10. Сохранение

- роверенная версия должна сохраняться после завершения соответствующего прохода.
- Формат Markdown должен сохраняться.
- одировка рабочих текстовых файлов: UTF-8 без BOM.
- осле сохранения необходимо проверять результат чтением файла или отдельной диагностикой.

---

## 11. апрет на слепое исправление

апрещается:

- выполнять массовую замену распространённых слов без контекста;
- заменять `при`, `для`, `после`, `пилот`, `должен` и подобные нормальные слова только по совпадению;
- переписывать документ целиком ради исправления одной ошибки;
- считать отсутствие результатов одного диагностического шаблона доказательством полной грамматической безошибочности;
- изменять содержание документа под видом грамматической очистки.

---

## 12. Статус грамматической проверки

роверка известных повреждений и общая проверка грамматики — разные задачи.

езультат:

**0 известных повреждений**

означает отсутствие ранее определённых типов повреждения.

то не означает автоматически отсутствие всех орфографических и грамматических ошибок.

ля утверждения о полной грамматической проверке требуется отдельный грамматический анализ и проверка его результатов.

---

## 13. абочий принцип проекта

> Сначала понять существующую документацию и правила проекта, затем изменить только необходимое, проверить результат и сохранить подтверждённую версию.

аждое новое согласованное правило добавляется в этот файл.
