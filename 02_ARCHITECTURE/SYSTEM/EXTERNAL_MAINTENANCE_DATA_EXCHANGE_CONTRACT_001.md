# ARCH-CONTRACT-EXT-MAINT-001 — External Maintenance Data Exchange Contract

## 1. Назначение

Документ фиксирует минимальный состав данных и правила обмена между BlueSky PRO и внешними специализированными системами технического состояния, технического обслуживания, ремонта и жизненного цикла БПЛА (MRO / CMMS / иные профильные системы).

BlueSky PRO не дублирует полноценную MRO-функциональность. Интеграция обеспечивает получение эксплуатационно значимого технического статуса и передачу данных, которые формируются в процессе эксплуатации БПЛА.

## 2. Архитектурное разделение ответственности

```text
BlueSky PRO                         External MRO / CMMS

Планирование и полёт               ТО / ремонт / ресурс
Эксплуатационные события           Технические записи
Mission / Flight                   Work Order / Maintenance Record
Операционный статус                Детальная история обслуживания
       │                                      │
       └──────── Integration Layer ───────────┘
```

BlueSky PRO не должна становиться Master System для специализированных записей ТО, ремонта и технической истории, если соответствующая функция выполняется внешней системой.

## 3. Master System

Для каждого объекта обмена заранее определяется система-источник истины (Master System).

| Объект данных | Master System | BlueSky PRO |
|---|---|---|
| Борт как эксплуатационный объект | BlueSky / согласованная система | источник/копия |
| Mission | BlueSky PRO | master |
| Flight | BlueSky PRO | master |
| Налёт и эксплуатационные события | BlueSky PRO | master |
| Техническое состояние | External MRO / CMMS* | отображение |
| Работы ТО | External MRO / CMMS* | статус/ссылка |
| Ремонт | External MRO / CMMS* | статус/ссылка |
| Ресурс компонентов | External MRO / CMMS* | критические значения/статус |
| Техническая документация | External MRO / DMS* | статус/ссылка |
| Роли BlueSky | BlueSky PRO Administrator | master |
| Технические допуски персонала | BlueSky PRO Engineer / согласованная система | master/отображение |

`*` Конкретная Master System определяется конфигурацией организации и конкретной интеграции.

## 4. Данные из BlueSky PRO во внешнюю систему

Передавать только данные, необходимые для технического учёта и обслуживания.

### 4.1 Flight / эксплуатация

- Mission ID;
- Flight ID;
- UAV ID / регистрационный идентификатор;
- дата и время;
- продолжительность полёта;
- суммарный налёт;
- циклы, если применимо;
- количество посадок, если применимо;
- идентификатор пилота/оператора в соответствии с правами доступа;
- эксплуатационные события;
- зарегистрированные отказы/предупреждения;
- идентификатор исходного flight log;
- версия конфигурации БПЛА.

### 4.2 Борт и конфигурация

- идентификатор БПЛА;
- тип/модель;
- серийный номер;
- текущая конфигурация;
- установленные компоненты;
- идентификаторы оборудования;
- идентификатор/версия конфигурации.

### 4.3 Батареи и компоненты

Если эти сведения доступны из полётной системы и требуются внешнему техническому контуру:

- идентификатор батареи/компонента;
- цикл;
- наработка;
- ключевые измерения состояния;
- предупреждение о выходе параметра за установленный предел;
- связь компонента с конкретным БПЛА.

Полный анализ ресурса и прогнозирование остаются функцией специализированной внешней системы, если она это поддерживает.

## 5. Данные из внешней системы в BlueSky PRO

BlueSky PRO получает не всю техническую базу, а нормализованный operational status.

### 5.1 Статус БПЛА

Минимально:

- `READY` — готов к эксплуатации;
- `ATTENTION` — требуется внимание;
- `MAINTENANCE_DUE` — требуется обслуживание;
- `MAINTENANCE` — находится на обслуживании;
- `GROUNDED` — эксплуатация ограничена/запрещена;
- `UNKNOWN` — актуальный статус не подтверждён.

Допускаются дополнительные статусы через зарегистрированный профиль интеграции.

### 5.2 События, требующие внимания инженера

- просроченное ТО;
- приближение срока ТО;
- достижение/приближение ресурса;
- выявленный дефект;
- ограничение эксплуатации;
- неисправность критического оборудования;
- отсутствие обязательной/актуальной документации;
- изменение конфигурации, требующее проверки;
- иные события, определённые правилами эксплуатации.

### 5.3 Технические документы

Передавать в BlueSky:

- тип документа;
- идентификатор документа;
- статус актуальности;
- срок действия, если применимо;
- применимость к БПЛА/компоненту;
- ссылку или внешний идентификатор записи.

Сам документ передаётся только при необходимости и в соответствии с политикой организации.

## 6. Что BlueSky показывает инженеру

На странице инженера используется агрегированный вид:

```text
СОСТОЯНИЕ ФЛОТА

БПЛА       ГОТОВЫ   ВНИМАНИЕ   ТО   НЕ ГОТОВ
24             17        4       2       1
```

Инженеру выводятся прежде всего объекты, требующие действия.

Пример:

```text
ВС-002   ▲ ТО через 12 ч
ВС-003   ▲ документ требует внимания
ВС-005   ▲ дефект
ВС-009   ▲ ресурс компонента
```

Подробная информация открывается по выбору конкретного БПЛА. Она не должна постоянно занимать рабочую область.

## 7. Персонал и технические допуски

Существующая модель полномочий сохраняется:

```text
ADMINISTRATOR
      ↓
назначает роли пользователю
      ↓
ENGINEER
      ↓
определяет технический допуск
      ↓
TECHNICIAN
      ↓
выполняет разрешённые работы
```

Интеграция может получать из внешних систем сведения о квалификации, обучении, сроках и иных условиях допуска, если это предусмотрено организационной моделью.

BlueSky не должна автоматически расширять полномочия пользователя на основании полученной информации.

## 8. Обмен результатом обслуживания

После выполнения работы внешняя система передаёт в BlueSky минимальный результат:

- идентификатор работы;
- БПЛА/компонент;
- тип работы;
- дата выполнения;
- результат;
- новый эксплуатационный статус;
- следующий срок/интервал, если применимо;
- ограничения;
- идентификатор исполнителя;
- ссылка/идентификатор первичной записи внешней системы;
- версия записи.

BlueSky связывает результат с соответствующим объектом и эксплуатационной историей.

## 9. Идентификаторы и трассируемость

Каждый обмен должен позволять однозначно связать:

```text
UAV
 ↓
Configuration
 ↓
Mission
 ↓
Flight
 ↓
Flight Data
 ↓
Maintenance Event
 ↓
External Record
```

Минимально используются:

- `UAV ID`;
- `Component ID`, если применимо;
- `Mission ID`;
- `Flight ID`;
- `External System ID`;
- `External Record ID`;
- `Correlation ID`;
- timestamp;
- версия данных.

## 10. Состояние синхронизации

Для каждого внешнего подключения BlueSky должна знать:

- подключение доступно/недоступно;
- время последней успешной синхронизации;
- актуальность полученных данных;
- наличие ошибок;
- наличие очереди необработанных сообщений;
- версию адаптера;
- версию внешней системы, если доступна.

Если данные устарели, BlueSky должна отображать это явно и не представлять неподтверждённый статус как актуальный.

## 11. Режимы обмена

Поддерживаются архитектурно:

1. REST/API;
2. webhook/event exchange;
3. файловый обмен;
4. импорт/экспорт по команде пользователя;
5. периодическая синхронизация.

Конкретный режим определяется адаптером внешней системы.

## 12. Нормализация

Внутренние модели BlueSky PRO не должны зависеть от внутренней структуры конкретного поставщика.

```text
External System A ─┐
External System B ─┼→ Adapter → Normalized Model → BlueSky PRO
External System C ─┘
```

Добавление нового поставщика должно выполняться созданием/настройкой адаптера и профиля совместимости, а не изменением ядра BlueSky PRO.

## 13. Ошибки и безопасность

Интеграционный слой должен обрабатывать:

- недоступность внешней системы;
- timeout;
- ошибку аутентификации;
- ошибку авторизации;
- несовместимую версию;
- повреждённые или неполные данные;
- дублирование сообщения;
- конфликт версии;
- устаревшие данные.

Должны применяться контролируемые retry/idempotency механизмы, где они применимы.

Credentials не хранятся в mission data, интерфейсе QML или пользовательских экспортных файлах.

## 14. Audit

Существенные операции обмена регистрируются:

- источник;
- назначение;
- тип операции;
- пользователь/сервис;
- дата и время;
- идентификаторы объектов;
- результат;
- ошибка;
- Correlation ID.

## 15. Граница интерфейса инженера

BlueSky PRO не должна показывать инженеру внутреннюю структуру внешней MRO-системы без необходимости.

Принцип:

```text
Внешняя система
      ↓
много технических данных
      ↓
Integration Layer
      ↓
нормализация
      ↓
инженерский operational view
      ↓
только требующее внимания
```

При необходимости инженер получает переход к первичной записи во внешней системе.

## 16. Применение к планированию полёта

Технический статус БПЛА должен быть доступен планировщику до назначения борта на миссию.

Минимальная логика:

```text
Mission
  ↓
выбор БПЛА
  ↓
проверка технического статуса
  ↓
проверка ограничений
  ↓
READY → допускается дальнейшее планирование
ATTENTION → предупреждение / дополнительная проверка
GROUNDED → не допускается
UNKNOWN → статус не подтверждён
```

Конкретные правила блокировки определяются отдельными требованиями безопасности и эксплуатации и не должны зашиваться в интеграционный адаптер.

## 17. Результат архитектурного решения

BlueSky PRO получает лёгкий и понятный инженерский контур без создания собственной сложной MRO-системы.

Внешняя специализированная система сохраняет глубокую техническую функциональность, а BlueSky PRO обеспечивает:

- связь эксплуатации с техническим состоянием;
- видимость готовности флота;
- предупреждения инженеру;
- контроль применимости технического статуса при планировании;
- двусторонний обмен необходимыми данными;
- трассируемость;
- независимость от конкретного поставщика MRO.

## 18. Статус решения

**ACCEPTED**.

Дальнейшее проектирование выполняется от настоящего контракта. Конкретные API, поля сообщений, JSON Schema, коды ошибок и адаптеры внешних продуктов разрабатываются отдельными спецификациями после выбора конкретной системы для первой интеграции.
