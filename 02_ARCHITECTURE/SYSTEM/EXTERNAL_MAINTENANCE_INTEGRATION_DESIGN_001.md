# 1. Решение

BlueSky PRO не реализует собственную полноценную MRO/CMMS-систему. Для технического состояния и обслуживания используется интеграционный контур с внешней специализированной системой.

Первым целевым классом интеграции принимается российская система управления жизненным циклом БПЛА, в частности «СТАР-БАС». Публично подтверждены цифровой паспорт, история полетов/ремонтов/замен узлов, автоматическое планирование ТО по налету, предиктивная аналитика, интеграция с 1С и другими программами через API. Публичной спецификации API «СТАР-БАС» в доступных источниках не обнаружено; поэтому конкретные endpoint'ы, поля авторизации и форматы сообщений пока не фиксируются как фактический API.

# 2. Цель интеграции

Получить в BlueSky PRO минимально необходимую для эксплуатации картину технического состояния флота и передавать во внешнюю систему эксплуатационные данные, влияющие на техническое обслуживание.

Главный принцип:

```text
Внешняя MRO/CMMS
      ↓
   Adapter
      ↓
Normalized Maintenance Model
      ↓
BlueSky PRO
      ↓
Engineer / Flight Planning
```

В обратном направлении:

```text
Flight / Mission / UAV Events
      ↓
Integration Layer
      ↓
Adapter
      ↓
External MRO/CMMS
```

# 3. Что является Master System

| Данные | Master |
|---|---|
| Mission | BlueSky PRO |
| Flight | BlueSky PRO |
| Эксплуатационный налет | BlueSky PRO |
| События полета | BlueSky PRO |
| Техническое состояние | внешняя MRO/CMMS |
| ТО и ремонт | внешняя MRO/CMMS |
| Ресурс компонентов | внешняя MRO/CMMS |
| История замен | внешняя MRO/CMMS |
| Техническая документация | внешняя MRO/DMS, если используется |
| Пользователи и роли BlueSky | BlueSky PRO Administrator |
| Технические допуски персонала | BlueSky PRO Engineer / согласованная внешняя система |

Звездочкой в реализации помечаются случаи, когда конкретная организация назначает другую Master System.

# 5. Поток данных после полета

```text
1. Полет завершен
       ↓
2. Flight log принят BlueSky
       ↓
3. Рассчитан фактический налет
       ↓
4. Сформирован Maintenance Event
       ↓
5. Integration Layer
       ↓
6. Adapter внешней системы
       ↓
7. Внешняя система обновляет технический учет
       ↓
8. BlueSky получает новый технический статус
       ↓
9. Инженер видит изменение
```

Не требуется отправлять весь flight log, если внешней системе достаточно нормализованных эксплуатационных показателей. Полный журнал остается в BlueSky и/или передается по отдельному контракту, если это требуется конкретной интеграцией.

# 6. Поток данных до полета

```text
Engineer / Planner
       ↓
Выбор БПЛА
       ↓
BlueSky запрашивает/читает последний Maintenance Status
       ↓
Проверка актуальности
       ↓
READY ─────────→ продолжить
ATTENTION ─────→ показать предупреждение
MAINTENANCE ───→ эксплуатационная блокировка/ограничение
GROUNDED ──────→ не допускать
UNKNOWN ───────→ показать отсутствие подтвержденного статуса
```

Конкретные правила блокировки должны находиться в отдельном safety/operational requirement и не должны быть частью адаптера конкретного поставщика.

# 7. Интеграционный слой

В BlueSky PRO создается не набор прямых соединений с внешними продуктами, а единый Integration Layer.

```text
                 BlueSky PRO
                      │
               Integration Layer
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
   STAR-BAS       1C / ERP       Other MRO
     Adapter       Adapter        Adapter
```

Каждый адаптер преобразует внешний формат в нормализованную модель BlueSky и обратно.

Ядро BlueSky не должно содержать условную логику вида `если STAR-BAS, то...`.

# 8. API как основной автоматический путь

Основной технический вариант — REST API с:

- HTTPS;
- аутентификацией по согласованному механизму;
- JSON для обмена структурированными данными;
- versioning API;
- idempotency для повторной доставки;
- correlation ID;
- timestamp;
- контролем версии записи.

Если внешняя система предоставляет иной протокол, адаптер скрывает его от ядра BlueSky.

Пока публичная документация конкретного API «СТАР-БАС» не подтверждена, данный раздел является проектным интерфейсом BlueSky, а не утверждением о фактическом API поставщика.

# 9. Синхронизация

Предусматриваются два режима.

### Pull

BlueSky периодически запрашивает:

- статус флота;
- изменения технического состояния;
- новые ограничения;
- результаты обслуживания.

### Push/Event

Внешняя система может передавать события:

- status changed;
- maintenance due;
- maintenance completed;
- defect registered;
- aircraft grounded;
- component changed;
- document status changed.

Конкретный режим определяется возможностями внешнего продукта.

# 10. Минимизация данных

BlueSky получает только то, что необходимо инженеру и планировщику.

На странице инженера не выводятся:

- внутренние таблицы MRO;
- вся история ремонтов без запроса;
- складская детализация;
- финансовые данные;
- служебные поля внешней системы;
- внутренние технические журналы, не влияющие на эксплуатационное решение.

При необходимости пользователь переходит к первичной записи внешней системы.

# 11. Надежность

Интеграция должна иметь:

- очередь исходящих сообщений;
- очередь входящих сообщений;
- повторную доставку;
- защиту от дублей;
- контроль целостности;
- контроль времени актуальности;
- журнал ошибок;
- журнал синхронизации;
- ручной повтор неуспешного обмена.

Если внешняя система недоступна, BlueSky не должна silently считать технический статус актуальным.

# 12. Отображение инженеру

Интеграция должна работать незаметно для основной работы.

```text
СОСТОЯНИЕ ФЛОТА

24 БПЛА

● 17  ГОТОВЫ
▲ 4   ТРЕБУЮТ ВНИМАНИЯ
■ 2   НА ОБСЛУЖИВАНИИ
● 1   НЕ ГОТОВ
```

Выбор события открывает конкретный БПЛА и причину.

Например:

```text
ВС-003
▲ ТО
До регламентного интервала: 8 ч
Источник: External MRO
Обновлено: 12:41

[Открыть запись]
```

# 13. Переход во внешнюю систему

BlueSky хранит `externalSystemId` и `externalRecordId`.

Если внешняя система предоставляет deep link, интерфейс может показать:

```text
[Открыть в системе ТО]
```

Если deep link отсутствует, отображается идентификатор первичной записи и доступный пользователю способ открытия внешней системы.

# 15. Приоритет реализации

### Phase 1 — базовая интеграция

- UAV identity;
- flight hours;
- cycles, если применимо;
- maintenance status;
- due dates;
- restrictions;
- external record ID;
- last synchronization.

### Phase 2 — техническая детализация

- компоненты;
- батареи;
- история замен;
- результаты ТО;
- документы;
- персонал/квалификация при необходимости.

### Phase 3 — расширенная аналитика

- отказовые события;
- статистика компонентов;
- предиктивные данные;
- аналитика эксплуатационной надежности.

# 16. Что НЕ проектируем сейчас

Не создаем внутри BlueSky PRO:

- полноценный складской модуль;
- собственную MRO-базу;
- полноценные work orders;
- ремонтные карты;
- управление закупками запчастей;
- полноценный документооборот ТО;
- предиктивную MRO-аналитику как отдельную систему.

Эти функции остаются внешнему специализированному контуру.

# 17. Основание решения

В 2026 году Ростех сообщил о создании российской платформы «СТАР-БАС» для управления полным жизненным циклом БПЛА. В ней заявлены цифровой паспорт, история полетов, поломок, ремонтов и замен узлов, автоматическое определение сроков ТО по реальному налету, предиктивная аналитика и интеграция с 1С и другими рабочими программами. Это подтверждает практическую целесообразность выделения технического жизненного цикла в специализированный контур, а не дублирования его в системе планирования.

Источники:
- Ростех: «При участии Ростеха создана первая в России система управления жизненным циклом дронов».
- Ростех: «Система управления жизненным циклом дронов включена в реестр отечественного ПО».
- Приказ Минтранса России от 18.10.2024 №367, ФАП «Техническое обслуживание ... беспилотных авиационных систем ... Часть 145».
