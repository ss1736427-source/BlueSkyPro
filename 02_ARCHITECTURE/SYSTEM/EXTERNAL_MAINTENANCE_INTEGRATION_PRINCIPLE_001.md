# BlueSky PRO — Principle of Future External Maintenance Integration

## 1. Назначение

BlueSky PRO проектируется с возможностью дальнейшего подключения внешних специализированных систем технического состояния, технического обслуживания, ремонта и управления жизненным циклом БПЛА.

На текущем этапе такая система не является обязательным компонентом BlueSky PRO и не создаётся как отдельный внутренний продукт.

## 2. Архитектурный принцип

**Интеграция должна быть заложена в архитектуру заранее, но реализация конкретного подключения выполняется только при возникновении практической необходимости.**

Это означает:

- ядро BlueSky PRO не зависит от конкретной внешней системы;
- внешняя система подключается через Integration Layer;
- для конкретного продукта создаётся отдельный Adapter;
- внутренние модели BlueSky не должны повторять структуру внешней MRO/CMMS;
- подключение внешней системы не должно требовать переработки ядра планирования и управления полётом;
- отсутствие внешней системы не должно нарушать штатную работу BlueSky PRO в пределах реализованной функциональности.

## 3. Цель

Сохранить возможность в будущем подключить специализированную систему без архитектурной переделки BlueSky PRO.

```text
                 BLUE SKY PRO
                      │
              INTEGRATION LAYER
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Adapter A   Adapter B   Adapter C
          │           │           │
          ↓           ↓           ↓
      Внешняя      Внешняя      Внешняя
      система      система      система
```

Конкретные внешние системы могут отличаться по API, структуре данных и протоколу обмена. Эти различия изолируются адаптером.

## 4. Что должно быть заложено уже сейчас

Даже без фактического подключения внешней MRO/CMMS в архитектуре BlueSky должны существовать расширяемые точки для:

- `UAV ID`;
- `Component ID`;
- `External System ID`;
- `External Record ID`;
- `Source System`;
- `Source Updated At`;
- `Last Sync At`;
- технического статуса;
- ограничений эксплуатации;
- событий технического состояния;
- ссылок на внешние записи.

Эти поля не означают наличие внешней системы. Они являются архитектурным резервом для будущей интеграции.

## 5. Принцип Master System

При появлении интеграции для каждого класса данных должна быть определена система-источник истины.

Например:

```text
Flight / Mission
      ↓
BlueSky PRO

Maintenance / Repair / Resource
      ↓
External MRO/CMMS
```

BlueSky не должна создавать конкурирующую запись истины для данных, владельцем которых является внешняя специализированная система.

## 6. Принцип минимизации

Интеграция не должна переносить в интерфейс BlueSky весь объём данных внешней системы.

В BlueSky отображается только информация, необходимая для текущего решения инженера или планировщика:

- готовность БПЛА;
- необходимость обслуживания;
- ограничения;
- критические дефекты;
- состояние ресурса;
- актуальность технической документации;
- дата последней синхронизации;
- ссылка на первичную запись внешней системы.

Подробная техническая история остаётся во внешней специализированной системе и открывается по запросу.

## 7. Принцип отсутствия жёсткой зависимости

BlueSky PRO не должна содержать бизнес-логику конкретного поставщика внутри ядра.

Недопустимая архитектура:

```text
Core BlueSky
   └── if STAR-BAS ...
```

Правильная архитектура:

```text
Core BlueSky
      │
Integration Interface
      │
Adapter
      │
External System
```

## 8. Принцип постепенной реализации

Интеграция реализуется поэтапно только при необходимости:

### Этап 0 — архитектурная готовность

- определить точки расширения;
- определить внутренние идентификаторы;
- определить нормализованную модель;
- определить события и статусы;
- не подключать внешнюю систему.

### Этап 1 — базовая интеграция

После выбора конкретной внешней системы:

- идентификация БПЛА;
- получение технического статуса;
- получение ограничений;
- сроки ТО;
- ресурсные показатели;
- дата актуальности;
- ссылка на внешнюю запись.

### Этап 2 — двусторонний обмен

- передача фактического налёта;
- передача эксплуатационных событий;
- получение результатов ТО;
- получение изменений технического состояния;
- синхронизация компонентов.

### Этап 3 — расширение

Только если это необходимо конкретной организации:

- документация;
- квалификация персонала;
- ремонт;
- ресурсные операции;
- аналитика;
- предиктивные данные.

## 9. Принцип выбора внешней системы

BlueSky PRO не должна архитектурно привязываться к конкретному поставщику до подтверждения:

- технической совместимости;
- доступного интерфейса обмена;
- требований безопасности;
- требований организации;
- состава передаваемых данных;
- ответственности за достоверность данных.

«СТАР-БАС» рассматривается как один из целевых вариантов внешнего специализированного контура, а не как жёстко зашитая зависимость BlueSky PRO.

## 10. Принцип для UI инженера

Будущая интеграция не должна приводить к появлению отдельного перегруженного раздела MRO внутри BlueSky.

Инженер продолжает работать в привычном интерфейсе BlueSky:

```text
ПАРК БПЛА

ВС-001   ● ГОТОВ
ВС-002   ▲ ТО
ВС-003   ■ НЕ ГОТОВ
```

При выборе БПЛА доступны основные эксплуатационно значимые сведения.

При необходимости:

`Открыть подробности → внешняя система`

Таким образом, интеграция расширяет возможности BlueSky, но не меняет её основной характер как системы планирования и управления полётами.

## 11. Критерий готовности архитектуры

Архитектура считается подготовленной к будущей интеграции, если добавление конкретной внешней системы требует:

1. реализации соответствующего адаптера;
2. настройки отображения нормализованных данных;
3. настройки правил синхронизации;
4. настройки безопасности и авторизации;
5. верификации обмена;
6. без изменения базовой логики планирования и управления полётом.

## 12. Статус решения

**ACCEPTED.**

Данный принцип является архитектурным ограничением для дальнейшего проектирования BlueSky PRO. Конкретный MRO/CMMS-поставщик, протокол, API и состав полей определяются отдельным проектом интеграции после возникновения соответствующей потребности.
